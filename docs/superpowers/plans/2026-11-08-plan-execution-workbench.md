# 自动安排执行绑定与成员协作台实施计划

> 基线：本地 main `8ee42490`；专项分支 `codex/plan-execution-workbench-20261108`。用户已确认优先级 1、2，评测随阶段推进。单线实施、自审，不使用子 agent。不自动提交、合并、推送、发布，不替换安装版或读取正式凭证。

## 要解决的问题与交付结果

目前自动安排保存了任务结构，但批准后仍发一句“按方案执行”，模型可以重新决定人数、分工和依赖。成员界面又把普通子任务、旧团队和 Bot 的能力分散展示，用户难以看出实际做到了哪里。

本轮让新自动安排在批准时冻结具体执行者、文件契约和任务映射，点击执行直接进入既有 Team 调度器；展示从批准的任务到真实成员、状态和宿主验收。旧方案和旧功能保持兼容。成员详情统一呈现当前职责、状态、阻塞和交付入口，操作仍按原后端真实能力提供。

## 设计边界

1. 方案 Markdown 是安排的唯一正文来源；在现有 `plans.json` 中保存批准时不可变执行快照。实时状态仍以 `team.json`、RunOverview 和宿主回执为准，不另建调度器或会话库。
2. 新安排显式标注可执行版本及每项具体 agent、TaskContract。提示提供当前可用 agent 名册；缺少执行信息必须补齐，不默认扩大权限。老方案不伪装成已绑定执行。
3. 复用冻结 TaskSettings、成员定义、原 DAG、原工具范围、产物锁、执行代次、证据验收和取消排空。任务数由模型按问题决定，受现有团队容量限制；映射使用短稳定 ID，不截断用户任务 ID。
4. 批准与执行分开。批准冻结版本，执行核对所属会话、当前分支、方案指纹和外部输入内容。重复执行幂等；失败可以重试开始，已运行或中断记录不自动重放。恢复仍要求明确操作。
5. 下游输入只采用已验收前置任务的产物版本。外部输入在批准时冻结。文本验收条件作为任务说明，不冒充可执行科研判据；结构化科学验收继续使用既有契约。
6. 本轮首先支持本地 Native 和现有本地 subagent。Bot 原有入口保留，远程/其他后端缺能力时明确提示，不静默绕过严格契约。
