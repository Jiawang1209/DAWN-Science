# 应用内升级的配置继承

用户确认的行为：应用内升级沿用原来保存的 API Key、R/Python 解释器路径和引导完成状态；真正首次安装且没有旧 DAWN 数据时，从四步第 1 页开始，由用户配置密钥与计算环境。手动重装保留旧数据时仍重新展示四步介绍，但原来的配置不删除。R/Python 沿用可稍后配置的约定。

解释器路径保存在用户数据库的 `interpreter.r` 和 `interpreter.python`，更新替换应用包不清理这份数据库。应用不复制或重新安装 R/Python；原路径仍有效时直接使用，路径失效时需重新选择。新用户库没有默认解释器路径。

凭证由旧进程在换包前导出并加密交接，新进程在系统存储预热后接收、重新加密，并清除临时交接文件。这次检查修复交接遗漏并明确当前配置优先规则：

1. 导出此前仅遍历 `entries`，遗漏 `undecrypted` 中已经恢复可读的密钥；现在取两者并集。
2. 接收此前用只包含模型服务商的 `broken()` 判断全部凭证是否可用，可能跳过视觉/MCP 等密钥；现在逐条检查交接条目。
3. 部分密钥不可读时，旧实现会同时覆盖用户刚填写的另一组有效密钥；现在只恢复仍保存但不可读取的条目，保留当前可读取的值。

4. 交接快照建立后若用户删除某个 Key，不会再把该条加回来。新增存在性判断只用于区分“已删除”和“保存着但解不开”，不会把仅存密文当作有效 Key。

接收逻辑从 Electron 入口抽为独立模块，不改变交接格式、系统授权、预热时序或用户数据路径。测试仅使用合成密钥，没有读取、输出或修改用户的实际密钥。真正无法读取的旧凭证仍明确报错，不把原密文当有效配置；这不是绕过系统授权的机制。
