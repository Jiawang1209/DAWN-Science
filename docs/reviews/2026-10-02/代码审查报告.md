## 首次审查确认的问题（以下描述为修复前行为）

P1 表示应优先处理的功能或数据可靠性问题；P2 表示特定条件下出现、需要安排修复的问题。每项均有独立诊断证据，严重程度依据实际影响判断。

### 1 P1 内核表达式结果没有返回给模型

位置：`src/tools/run-code.ts:80`。

`摘要()` 处理 `result` / `display` 时，对于非图片输出也只返回“已经显示在对话里”，没有读取实际 `data`。因此 Python 单独执行 `42`、`df.head()` 或其他通过 Jupyter `execute_result` 返回的结果，人可以在界面上看到，模型收到的工具结果却没有该值。stdout 的 `print(...)` 路径正常，因此表现会随代码写法改变。

诊断输入 `{kind: "result", mediaType: "text/plain", data: "42"}`，实际摘要不包含 `42`。代码注释只要求图片不进入模型上下文，当前处理范围扩大到了文字结果。

建议：在保持图片隔离和输出字节上限的前提下，将可读文字结果返回给模型，并为多 MIME 输出保留适合模型的文字表示。补上表达式结果、表格文字回退和输出截断测试。

### 2 P1 数据差异把零值改变误判成整列缩放

位置：`src/files/table-diff.ts:131`。

识别整列乘一个因子时，代码跳过所有旧值为零的单元格，没有检查新值是否仍为零。随后整列被标为“缩放”，逐格检查又跳过这整列，导致实际数据改变被隐藏。

复现：旧列 `[0, 1, 2]`，新列 `[999, 1000, 2000]`。实际输出为“整列乘 1000”，`单元格总数: 0`；但第一格 `0 → 999` 显然不属于缩放。这会误导科研数据改动审阅。

建议：只有 `0 → 0` 才能忽略；任何 `0 → 非零` 必须否定纯缩放判定，或在缩放摘要之外明确报告例外。测试正负零、缺失值和新增行。

### 3 P1 并发下载同名文件没有保留独立目标路径

位置：`src/workbench/backend.ts:778`、`:3895`；下层写入为 `src/remote/ssh.ts:445`。

“不覆盖的名字”只检查完成后的目标文件是否存在，不检查正在进行的传输，也不预占路径。第一个下载尚未完成时，第二个同名下载会取得同一个目标。下层又使用固定 `${本地}.dawn-part` 临时文件，因此两次传输会共用最终路径和临时文件。

诊断让两个下载都保持进行中：`/server-A/result.csv` 与 `/server-B/result.csv` 实际取得同一个本地 `result.csv` 路径。目标冲突已通过真实后端入口复现；诊断用受控传输替身，不连接用户服务器。相互截断、改名失败或清理掉另一次传输的临时文件，是结合下层文件写入代码确认的风险，本次未故意损坏真实下载文件。

建议：在启动时原子预占目标，统一考虑运行中的传输；每次传输使用独立临时文件。上传也使用固定临时名，应一并检查并发上传同一目标的处理。

### 4 P2 分隔符识别把引号内的字符算作字段分隔符

位置：`src/files/table.ts:64`。

`认分隔符()` 直接统计第一行的逗号、制表符和分号，没有忽略引号内部的字符。合法 CSV 表头中的分号数量多于真正的逗号时，会被误读为分号表。

复现：

```csv
"id;group;note",value
a,1
b,2
```

实际识别为分号分隔、只有一列，数据行成为 `"a,1"` 和 `"b,2"`。正确结果应是两列。后面的字段解析虽然支持引号，但分隔符已经选错，无法补救。

建议：只统计引号外的候选分隔符，结合多条完整记录的一致列数识别；增加引号内逗号、分号、制表符和转义引号测试。

### 5 P2 相同记忆建议会跨项目或分支合并

位置：`src/memory/queue.ts:88`；调用入口为 `src/tools/memory/index.ts:69`。

建议队列是全局共用的，而去重条件只比较 `target` 和归一化后的正文，没有比较 `workspace` 或 `branches`。两个项目分别提出相同的 `key` 建议，第二条只增加第一条的命中次数，保留第一条的项目和分支信息，却把理由改为第二条的理由。

复现：项目 A 的 `main` 分支与项目 B 的 `dev` 分支都提出“原始数据只读”。实际只剩一条建议，工作区为 A、分支为 `main`、理由来自 B。用户采纳后 B 的建议没有写入 B。相同项目的不同分支也有同类问题。

建议：`key` 建议的去重键应包含规范化工作区和规范化分支集合；全局轨与项目轨分别处理。

### 6 P2 采纳记忆时存储抛异常会永久丢失建议

位置：`src/workbench/backend.ts:2942`、`:2956`。

`memoryResolve` 先调用 `queue.take()`，再写入记忆。只有存储返回 `{ok: false}` 时才放回队列；真正的文件系统异常或锁异常没有被捕获，建议已被移出队列，存储又没有成功。

诊断使用真实 `MemoryStore` 和临时目录，让项目 `.dawn` 路径成为一个普通文件，产生实际文件系统异常。采纳操作抛错后，待确认队列数量由 1 变为 0。全过程只操作独立临时目录。

建议：为取出、写入、完成这一流程提供事务语义或异常回滚；返回失败和抛出异常都应保留待确认建议，并明确反馈。

### 7 P2 未来起始日较远时下一次运行时间错误返回空

位置：`src/schedule/recurrence.ts:99`。

`everyDays` 从查询当天开始，只向后搜索 `everyDays + 1` 天；没有先跳到计划的 `start` 日期。起始日超出搜索窗口时，即使计划有效，`下一次()` 也返回 `null`。

复现：查询时刻 `2026-10-02T00:00:00Z`，起始日 `2026-11-01`，每 2 天、上海时间 09:00。正确下一次是 `2026-11-01T01:00:00.000Z`，实际为 `null`。

影响是下一次运行时间和最近到期汇总错误。调度器有最多 60 秒的轮询，进入起始日附近后仍可能重新算出任务，不能据此断言任务永远不会运行。

建议：每 N 天规则应从 `max(当前本地日期, 起始日期)` 或日历差直接计算下一次，再比较具体时间。

### 8 P2 夏令时缺失小时被映射到更早的时间

位置：`src/schedule/recurrence.ts:65`。

本地时间转 UTC 采用两轮偏差修正；夏令时开始当天的不存在时间会在前后两个小时之间振荡，固定两轮后可能选到更早的解，与代码声明的“空洞取靠后的解”不一致。

复现：纽约 `2026-03-08 02:30`（当天这个时间不存在），实际返回 `2026-03-08T06:30:00.000Z`，即当地 01:30，而非顺延后的 03:30。

上海时区不受该场景影响；使用有夏令时的时区时，会产生提前运行或错过目标时间的问题。

建议：明确不存在时间和重复时间的处理规则，转换后反向核对本地分量，并覆盖春季跳时、秋季重复小时和非整小时偏移时区。
