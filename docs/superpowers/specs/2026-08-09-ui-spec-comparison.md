# 对照报告：作者提供的 Codex Desktop UI 规范 vs DAWN 现状

- **日期**：2026-08-09
- **来源**：`/Users/liuyue/Desktop/Github_repos/ccb_hive_code_learn/learn_UI`
  （`CODEX_DESIGN_SPEC.md` · `ARCHITECTURE_ANALYSIS.md` · 一套 CSS + 一个 vanilla HTML 原型）
- **本报告不改代码。** 它回答三个问题：能直接拿的是什么、要改造的是什么、与既有决定冲突的是什么。

---

## 0. 一句话结论

> **可以拿的是「几何」与「结构」，不能照抄的是「颜色」。**
>
> 那份规范的颜色是**从一台跑着 Dracula 主题的机器上量出来的**——
> 照抄 §2.1 的表面色，得到的不是「像 Codex」，是「像 Dracula」。

---

## 1. 最要紧的一处发现：颜色是主题委托的，不是产品身份

`CODEX_DESIGN_SPEC.md` §2.1 给了一张「暗色主题表面色」表：

```
Canvas   #21232d      主内容区 #282a36      主文字 #f8f8f2
--color-accent-blue: #ff79c6   /* Dracula pink */   ← 文档自己标了
```

`#21232d` / `#282a36` / `#f8f8f2` / `#ff79c6` 是 **Dracula 配色**，
而 §2.2 的调色板（`--gray-0..1000` = `#ffffff`…`#0d0d0d`）是**另一套**——
两节的数据来自两个不同的层。

`ARCHITECTURE_ANALYSIS.md` 解释了为什么：

- Codex **完整继承了 VS Code 的主题变量体系**（`--vscode-*`，约 250 个）
- 内置 **116 套代码高亮主题**（dracula / nord / tokyo-night / catppuccin …）
- 主题策略是 `.dark` / `.electron-dark` / `.electron-light` 三态共存

**这与 ①-B″ · V2 时记下的结论一致，并且更锋利**。当时的原话是：

> *另发现：**那个应用自己没有强调色**，整套色相委托给 VS Code 的当前主题——
> `#10a37f` 是 DAWN 自己定的。*

现在有了实测数据：**连表面色也是委托的**。所以：

| 那份规范里的 | 是产品身份吗 | 能不能拿 |
|---|---|---|
| §2.1 表面色（`#21232d` 等） | ❌ 是那台机器当时的主题 | **不能照抄** |
| §2.2 调色板（gray/blue/green…） | ⚠️ 是 OpenAI 的品牌色阶，但**规范里的表面色没用它** | 可作参照 |
| §3 尺寸 / 间距 / 圆角 | ✅ 与主题无关 | **可以直接拿** |
| §4 排版（字号 / 字重 / 字体族） | ✅ 与主题无关 | **可以直接拿** |
| §6 按钮状态（`color-mix` 百分比） | ✅ 是**相对量**，与具体色值无关 | **可以直接拿** |
| §5 类名体系 | ❌ 真实应用用的是 CSS Modules 哈希（`_ComposerFooter_1i340_2`） | **不能拿** |

**§5 那些 BEM 类名（`app-composer__footer`）是原型作者自己起的**，不是从应用里量到的——
原型的 `app.html` 与规范 §5 引用的 DOM 不是同一套东西。

## 2. 能直接拿的（与主题无关，且我们现在没有）

| 项 | 规范里的值 | 我们现状 |
|---|---|---|
| Header 高度 | **46px** | 无固定令牌 |
| 侧边栏宽度 | `clamp(240px, 275px, min(520px, 100vw - 320px))` | 固定值 |
| 列表行高 | **30px** | 无 |
| 行内边距 | x **8px** / y **4px** | 散落各处 |
| 面板内边距 | 12px；工具栏 16px | 散落各处 |
| Composer 最大宽 | **768px**，文本区 712×44 | 无上限（满宽） |
| 圆角体系 | 9 级 + **全局缩放 ×1.25** + `superellipse(1.5)` | 少数几个字面值 |
| 聊天字号 | 14px / 代码 12px | 12–14 混用 |
| 按钮三态 | `color-mix(in oklab, base N%, transparent)` | 手写 hover 色 |

**这一栏是这份规范最大的价值**：它把「看起来像样」拆成了可执行的数字。
我们现在这些值大多是我凭手感定的，**没有依据**。

## 3. 与既有决定冲突的：令牌体系

| | 那份 UI | DAWN 现状 |
|---|---|---|
| 调色板层 | 131 个（`--gray-0..1000` / `--blue-*` …） | — |
| 语义层 | 166 个（`--color-background-surface` / `--color-text-primary` …） | — |
| 数字分级 | — | **43 个**（`--dawn-text-1..4` / `--dawn-surface-*` / `--dawn-stroke-1..3`） |

**①-B″ · V2 明确决定过不走语义角色那条路**：

> *一处刻意不学：Codex 有 1,366 个语义角色令牌。我们 ~30 个数字分级令牌。
> **两种都对，取舍不同**——语义角色在调用点自解释但数量爆炸，
> 数字分级紧凑可派生。我们的规模用数字分级是对的，不跟着膨胀。*

**那个判断在当时是对的，但前提变了**：当时我是隔着构建产物猜，
现在手里有一份实测规范。**有规范的时候，语义层的成本主要在「谁来写」，
而它已经写好了。**

不过要注意：**采用两层令牌不等于要 297 个**。我们可以只取
「调色板 + 语义」这个**结构**，各层只放我们真正用得到的那些。
**结构的价值在于「改配色时只动调色板」，与令牌数量无关。**

---

## 4. 那份原型没有、而我们有的

- **项目概览面板**（状态 / 产出 / 变更 / 成本 / 上下文 / 历史）
- **终端视图**（PTY 会话）
- **子 agent chip 组**

这三块规范里没有对应形态，得我们自己定。**这是加，不是冲突。**

---

## 5. 三条路，与各自的代价

| | 做什么 | 代价 | 拿到什么 |
|---|---|---|---|
| **A · 只吃几何** | 把 §3/§4/§6 的数字变成令牌并应用 | 8 张视觉基线重存；`design-contract` 扫描要加几条 | 布局立刻「有依据」了；**配色不变** |
| **B · 几何 + 两层令牌** | A + 把 43 个令牌重构成「调色板 + 语义」 | A 的代价 + `tokens.css` 重写 + 全部 CSS 引用改名 | 以后换配色只动一层 |
| **C · 整套照搬** | B + 类名改 BEM + 复刻 Dracula 配色 | B 的代价 + 所有组件与 e2e 定位器要动 | **不推荐**——配色是别人主题，类名是原型作者自己起的 |

**我的建议是 A，然后看效果再决定要不要 B。**

理由：**A 的收益最实、风险最低**——它修的是「数字没有依据」这个真问题，
而完全不碰配色（配色现在是你定过的 OpenAI 绿，不是没想过的东西）。
B 是结构性重构，值得做，但应该在你看过 A 的效果之后再决定，
**而不是一次把两件事捆在一起——那样红了分不清是几何不对还是令牌不对**。

C 里唯一值得单独拿的是 **`superellipse(1.5)` 圆角**，那是它视觉气质的一部分，
且与配色无关，可以并进 A。

---

## 6. 无论选哪条，有两件事要先做

1. **`docs/DESIGN.md` 要跟着更新**。它是视觉与交互契约的家，
   新令牌与新数字必须写进去，否则下一个人还是照手感来。
2. **`design-contract.test.ts` 要加扫描**。准入规则 ②：能判定的设计规则配一个扫描测试。
   例如「不许出现字面 px 值，一律用令牌」——**这一条现在就违反了很多次**。
