# 远端 R 内核 · 设计

> 2026-09-05。分支 `remote-r`。**改写 `2026-09-03-远程内核-design.md` 里关于「文件是内核自己写的」那一条**——
> 那句话对 ipykernel 成立，对 IRkernel 不成立。

## 为什么现在做

仓库的公开描述与 README 都写着 *"multiple agents collaborate with you on **R and Python** data science"*，
v0.0.2 已经发到 GitHub Releases。而**远端 R 这条路一次都没跑过**：

- Spike F（08-11）只测了 Python；
- 假服务器只接了 `DAWN_FAKE_SSH_PYTHON`，R 的起内核命令被它认出来后直接回 127（「假服务器只会起 python 内核」）；
- 作者 09-04 在真集群上验的也是 Python。

上线之前这叫「没验」，上线之后它是**对外承诺了但没有任何判据兜着**。

## 量出来的三件事实（2026-09-05，本机 R 4.6.1 + IRkernel）

1. **`IRkernel::main(connection_file = "")` 只读不写。** 源码就三行：文件名从 `commandArgs(TRUE)[[1]]` 取，
   然后 `Kernel$new(connection_file = …)`。给一个不存在的路径，它报
   `Error in open.connection(con, "rb") : cannot open the connection` 后**立刻退出**。
   → 09-03 规格里「`-f "$f"` 指向一个不存在的路径时 ipykernel / IRkernel 会自己挑端口、生成 key、
   把 connection.json 写在那儿」**这句话里的 IRkernel 是错的**，而且这个错足以让远端 R 在真集群上完全起不来。
2. **给了合法的 connection.json，IRkernel 0.4 秒内把五个端口都听上了。**
   → `起远端内核` 里那句「30 次 × 500ms 在 IRkernel 冷启动上偏紧」的猜测不成立，慢的不是启动。
3. **R ≥ 4.0 的 `serverSocket(port)` 可用**（本机 4.6.1 实测），所以「挑几个空闲端口」这件事
   可以让**服务器上的 R 自己**做——不必假设那台机器上有 python（`server-gets-no-files` 那条硬约束下，
   我们也不能传一个挑端口的脚本上去）。

## 定案

### R1 · 连接文件由我们写，端口由远端的 R 自己挑

起 R 内核分两条命令（两趟 SSH，各自失败各自报）：

```
① R --slave -e '<挑端口 + 写文件>' --args <文件> <key>   → 回 DAWNPORT_shell=… ×5、DAWNRC=0
② nohup $s R --slave -e 'IRkernel::main()' --args "$f" & → 与 python 那条同一个形状（不改）
```

①里的 R 脚本只用 base R：在 `20000..60000` 里随机取候选，`tryCatch(serverSocket(p))` 成功就留着
（**五个 socket 全开着直到都挑完**，否则会挑到同一个端口），最后一起 `close()` 再写文件。
上限 200 次尝试，挑不满就 `DAWNRC=3` 如实报（不许退化成「随便写五个数」——那会变成
「内核起不来但我们不知道为什么」）。

**为什么不在本地挑端口**：那是我们这台电脑的空闲端口，与服务器无关。共享登录节点上跑着
别人的 jupyter 是常态，撞端口的后果是内核起来就死，而症状会伪装成「R 装得不对」。

**race 窗口**：①的 R 进程退出（socket 关闭）到②的 IRkernel 绑上，中间有几十毫秒的空窗，
别人恰好抢走的概率极低。jupyter 自己也是这么做的，不额外处理，但要让绑不上时的日志能被人看见（见 R2）。

### R2 · R 的就绪判据不是「connection.json 出现了」

Python 那条靠轮询文件出现来判断内核起来了；**R 的文件是我们自己先写的**，那条判据对 R 恒真、
什么也证明不了。R 走另一条：

- 起完之后轮询 `活着脚本`（进程在不在），**连续几次都活着**就返回我们写下的连接信息；
- 起来就死（Rscript 路径不对、IRkernel 没装、文件权限不对）在第一次轮询就被抓到，
  照旧抛 `远端启动失败` 并带上 `.log` 尾巴——**那是唯一的线索，必须带出去**；
- **真正的就绪由后面的握手证明**（`attachKernelChannel` 的 `kernel_info`）。握手失败时同样要把
  `.log` 尾巴捞出来，否则用户看到的是「握手超时」，而日志里写着的是 `there is no package called 'IRkernel'`。

### R3 · 我们写的 connection.json 必须是 0600

里面有 HMAC key。集群是共享机器，`$TMPDIR` 常常是所有人可读的 `/tmp`。
`umask 077` 之后再写（ipykernel 自己写的那份本来就是 0600，python 那条不受影响）。

### R4 · 假服务器要能真起 IRkernel（准入规则 1）

`DAWN_FAKE_SSH_R` 镜像 `DAWN_FAKE_SSH_PYTHON`：事实脚本里报这条 R 的路径、探测命令真 spawn 它、
起内核真 spawn 一台本机 IRkernel、扫残留真杀。**没设这个环境变量时照旧回 127 并说清「不是没装 R，
是这台假机器不支持」**——不假装能起。

### R5 · `dev:mock` 自动找一条带 IRkernel 的 R

与自动找 python 同一个形状。找不到就说一句，不静默。

## 不做（记下）

- **Windows 上的远端 R**：远端是 Linux/mac，与本机平台无关，不额外做。
- **`--slave` 换 `--no-echo`**：R 4.2 起 `--slave` 是别名，仍然可用；换了会丢掉对老 R 的兼容，不划算。
- **端口范围可配**：先写死 `20000..60000`；真撞上再说。
- **R 的远端变量面板 / 图**：走的是同一条通道代码，不是 R 专有的一块。e2e 会验它们真的回得来。
