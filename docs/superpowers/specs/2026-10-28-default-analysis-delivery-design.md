# 默认分析交付规范

状态：设计稿；用户已认可默认交付规范、复用内置 skill 与程序保证关键内容的方向，并明确报告只需记录采用哪个脚本及如何调用，不嵌入脚本全文。尚未修改业务代码或技能。

## 目标与触发

分步骤保存普通脚本和结果，最后形成一份可以连续阅读的 Markdown 分析报告。用户要求“整理分析”“完整分析报告”“交给合作者”，或进入现有整理交付功能时默认采用；普通探索、临时检查、只解释结果时不自动创建交付。用户明确指定其他格式时遵循用户要求。

扩展已有 `skills/analysis-delivery/SKILL.md`，不新增重复技能、工作模式或一轮配置。现有项目选文件入口、仅整理/整理并验证以及独立运行核对继续使用。

## 文件与报告结构

新交付以 `分析报告.md` 为主要阅读入口，升级现有 `结果解读.md` 的职责，不同时生成两份内容重复的主报告。`README.md` 保留简短的目录、运行说明和指向报告的入口。独立 `.py`、`.R` 文件与选定图表仍然保留。

报告按以下结构组织：

1. 分析目的、数据来源、实际采用文件及已知环境。
2. 按步骤组织分析：步骤目的、采用脚本的可点击路径、调用命令、关键参数与输入输出、对应图表或表格链接、结果说明。报告不嵌入脚本全文。
3. 主要发现与适用范围；实际证据支持的数字、限制和未确认事项。
4. 运行顺序、命令与依赖；实际整理及验证状态。

步骤顺序优先沿用用户说明或已有的步骤编号。无法确认的依赖或执行顺序明确说明，不把文件排序当作验证过的执行顺序。模型无法归入某一步的已选脚本单列为待确认引用，不凭空声称已经使用。实际科学解释仍以现有证据规范约束，程序不能替模型证明解释正确。

旧交付记录和原报告文件保留，读取继续兼容原有 interpretation 角色；新建交付才采用新报告名称及结构。

## 模型与程序分工

模型提供步骤标题、说明、结果解读与对已选文件的引用关系，依据已有运行记录或脚本中的明确用法整理调用方式。程序校验引用属于本次采用的文件，不接受凭空出现的脚本或结果路径。

程序负责：

- 保留本次采用的独立脚本副本，并在报告中引用同一份文件；不为报告重新读取可能已经被覆盖的工作区路径，留存版本沿用确切留存字节。
- 报告记录脚本路径和调用命令，不复制代码全文。已有真实调用记录时优先引用；仅能从脚本用法整理出命令时标为“建议调用方式，未执行”，无法确认参数时明确缺口，不编造实际执行记录。
- 依据实际复制位置构造图片、表格和脚本相对链接，正确编码空格等路径字符；只引用已选文件，不自动收集整个项目或把输入数据全量复制。
- 检查报告引用的脚本和结果是否在交付中实际存在，调用说明中的脚本目标是否与引用一致。只检查能确定的目标与状态，不宣称已经验证任意命令的全部语义。沿用现有读取与复制预算；文件超限、不可读、文本编码不支持时列出缺口。
- 将整理是否完整与执行验证状态分别记录。选定或复制脚本不代表脚本已经执行，更不代表整个项目没有其他依赖或科学结论正确。

模型解读可以引用证据，程序负责实际文件链接与状态的一致性；不新增代码逐字嵌入、比对流程。描述未知依赖、方法或参数时继续明确未知。

## 原脚本与重新整理脚本

用户已经按步骤保存的脚本直接采用，不默认要求再合成一份项目总脚本。读取到脚本仅能证明文件存在，只有实际记录或运行验证支持时才标为已执行。

没有保存脚本时，技能可以依据真实成功步骤整理代码，并说明它是后续整理的版本。交付功能只取得所选文件时，不从图片反推代码；缺少脚本仍可生成有缺口的报告。

现有独立运行验证若确实需要另外生成带输入/输出参数的入口，保留该能力；报告单列“整理后的验证脚本”的路径与调用方式，与当时使用的脚本明确区分。验证结果沿用真实运行记录。

## 技能与界面

`analysis-delivery` 写入相同的触发、报告结构、分步脚本优先、脚本引用与调用说明、真实状态要求。普通对话内依技能写文件时也采用这一规范；程序保证只适用于实际经过交付服务生成的报告，不宣称任意模型自行写出的 Markdown 都已程序校验。

现有交付按钮文案改为阅读分析报告，并说明报告包含脚本调用说明及结果解读。沿用项目文件选择和现有状态展示，不增加新面板或额外的代码展示选项。
