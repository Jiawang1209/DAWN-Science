# 回到底部浮标 —— 跟随停了，出路要看得见

**2026-09-08** · 分支 `fixbug-0908-input`

## 从哪来

作者报：*「分析的内容不更新，需要我手动往下挪动。」*

同一天已经修掉一条真根因：`use-stick-to-bottom@1.1.6` 那个模块级 `let mouseDown`
会因为丢掉一次 `mouseup` 而永远为真，贴底动画于是每帧空转
（见 `src/ui/mouse-stuck.ts` 与 `e2e/stick-to-bottom.spec.ts`）。

但那条修完，**这句话里还剩一半没被回答**：

> 「需要我**手动往下挪动**。」

查下来是真的：**整个界面里没有任何一个「回到底部」的入口**——
`scrollToBottom` / `useStickToBottomContext` 一处都没用过。

这个库的行为本身是对的：**你一旦主动上滚，它就撒手**
（不然你翻上去看前面说了什么，下一个 token 又把你弹回底部）。
问题在于**撒手之后没有出路**：屏幕上既没有东西告诉你「跟随停了」，
也没有任何一键回去的办法。

按本项目自己那条规矩，这就是**「看不见的能力等于不存在」**——
2026-08-10 一天之内犯过两次（没标签的 `＋`、`opacity: 0` 的裸 `×`），
两次作者的反馈都是「没有这个功能」，而两次代码都是好的。

**所以这一条不是修 bug，是补一个入口。**

## 长什么样（作者定的）

**2026-09-09 改过一次形状。** 第一版按作者当时的选择做成了「右下角一颗圆的 `↓`」，
他看到实现之后的话是：*「这个按钮太丑了，我们做成方案1设计的样式吧。」*
方案一就是当初提的第一个选项——**底部居中的带字药丸**。

（这一条又印证了那件事：**版面形状的选项要配图，而且图不如实物**。
三个选项都配了 ASCII 图，他仍然是看到真东西之后才改的主意。）

```

┌────────────────────────────┐      ┌────────────────────────────┐
│  agent: ……分析结果如下……    │      │  agent: ……分析结果如下……    │
│                            │      │                            │
│  agent: ……                 │      │  agent: ……                 │

│      │ ↓  回到底部   │      │      │      │ ↓  有新内容   │      │
│      ╰──────────────╯      │      │      ╰──────────────╯      │
├────────────────────────────┤      ├────────────────────────────┤
│ ┌────────────────────────┐ │      │ ┌────────────────────────┐ │
│ │ 今天帮你做些什么？      │ │      │ │ 今天帮你做些什么？      │ │
│ └────────────────────────┘ │      │ └────────────────────────┘ │
└────────────────────────────┘      └────────────────────────────┘
```

**两个状态都带字**，这不只是好看：设计契约禁原生 `title`
（无样式、约 500ms 系统延迟、与主题不符），所以那颗光秃秃的圆点**悬停什么都不出**，
只有读屏能知道它是干嘛的。带上字之后这条代价整个消失——
**可见文字就是它的可访问名**，连 `aria-label` 都不需要。

**居中还有一条实在理由**：转录本身就是居中的一栏（768px 上限），
靠右下角那颗离正文很远，视线要横着走一趟才够得着。

## 三个状态，判据全部来自库自己

| 什么时候 | 画什么 |
|---|---|
| `isAtBottom` | **什么都不画**——跟随好好的，不该有任何东西挡着 |
| 没贴底、内容没长过 | 「↓ 回到底部」 |
| 没贴底、内容长过 | 「↓ 有新内容」 |

点一下 → `scrollToBottom()`，跟随恢复，「长过」清零。

## 它挂在哪（量过 DOM，不是想的）

`<StickToBottom>` 渲染的外层 `div` 就是我们的 `.turns`，
**真正在滚的是它里面那一层**（`.turns > div`，库自己造的 `height:100%` 那个）。
这一点 2026-09-08 在真产物上量过：`.turns` 的 `scrollHeight` 恒等于 `clientHeight`，
量错元素会得到一组「永远贴底」的假数字。

于是浮标放成 `<StickToBottom.Content>` 的**兄弟**：

```
<StickToBottom className="turns">     ← 不滚。position: relative 挂这儿
  <StickToBottom.Content .../>        ← 里面那层才滚
  <回到底部 />                         ← position: absolute，底部居中，不跟着滚
</StickToBottom>
```

`.turns` 本来就 `overflow: auto`，绝对定位的子元素被裁到它的内边距框——
正好就是我们要的「转录区底部」。居中靠 `left: 50%` + `translateX(-50%)`；
输入卡在 `.turns` 外面，不会被压着。

## 「底下长出新东西了」怎么知道

**组件自己用 `ResizeObserver` 盯 `context.contentRef`**：没贴底的时候内容高度长了，
就是底下多出东西了。

不让调用方传一个「记号」进来，有两条理由：

1. **流式回复时 `items.length` 不变、内容却在长**。传数字那种做法会漏掉
   最常见的那一种情况——而那正是作者报的场景。
2. 对话区和笔记本因此是**同一份代码、零配置**。传参的话两处各算一遍
   「什么算新内容」，而两处早晚会算得不一样。

## 装几处

**两处一起装**：对话区（`views.tsx`）与笔记本那一格（`notebook.tsx`）——
它们用的是同一个贴底库。

这个项目吃过「同一条规则只套了一半」的亏：粘贴图片当初只给了对话那个输入框，
**而应用打开就落在空态卡上**，于是最常见的那一次粘贴恰恰是不工作的那一次
（2026-08-13 作者报的）。同一份代码放两处，不给第二次机会。

## 文案

| | zh | en |
|---|---|---|
| 常规 | 回到底部 | Jump to latest |
| 底下长出过新内容 | 有新内容 | New messages |

两条都是**可见文字**，不写 `aria-label`、不写 `title`。

两条都要过 `tests/ui/design-contract.test.ts` 那两条扫描：
**没有一个按钮文案是另一个的子串**、**`aria-label` 与按钮文案之间也没有子串关系**。
实现时跑一遍确认，撞了就换说法——不为了躲子串把它藏起来。

## 怎么验

- **e2e**（`e2e/stick-to-bottom.spec.ts` 续写，跑真实构建产物）：
  1. 往上翻 → 浮标出现 → **点它** → 回到底部，且此后新内容照旧跟随；
  2. 翻上去之后新内容到达 → 文案变成「有新内容」；
  3. **贴着底时一个像素都不许画**——这条是防它变成常驻遮挡物的那道闸。
  三条都先红后绿。
- **单元**：「这一刻该说什么」这条判据单独验（不依赖真滚动），
  外加一条「两个可见状态说的话不一样」——两处长得一样的东西等于没有判据。
- **十张视觉基线**：浮标贴底时不画，理论上一张都不该动。**跑一遍确认**；
  红了先看 `test-results/<用例>/<名字>-diff.png`，不条件反射 `--update-snapshots`。

## 不做的

- **不做「未读几条」计数。** 我们没有「读过」这个概念，数出来的数字会撒谎。
- **不做自动滚回去。** 撒手是这个库的正确行为，人翻上去就是想看前面——
  自动拽回去正是它当初要解决的问题。
- **不给侧栏 / 命令面板再加一个入口。** 这个动作只在「你正看着转录、
  而它没贴底」时有意义，那时浮标就在眼前。
