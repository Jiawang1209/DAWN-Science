# 写一个技能

用户让你「把这个记下来」「做成技能」「以后都按这个来」时，**你自己写文件就行**，
不需要他去点任何按钮。

## 什么时候用

- 用户说：把这套做法记下来 / 做成一个技能 / 以后都这么干 / 存成模板
- 你们刚一起摸索出一套可复用的做法（某类数据的清洗顺序、某种图的画法）
- 用户抱怨「每次都要跟你说一遍」——**那就是该写技能的信号**

## 什么时候不要用

- 一次性的做法（只对这一份数据成立）——写进技能只会污染以后每一段对话
- 用户只是想要一段代码 → 写成 `scripts/` 下的脚本，不是技能
- 内容是**这个项目的事实**（数据在哪、字段什么意思）→ 那属于 `AGENTS.md`，不是技能

## 格式

一个技能 = **一个文件夹 + 一个 `SKILL.md`**：

```
.dawn/skills/soil-eda/SKILL.md
```

```markdown
---
name: soil-eda
description: 一句话说清「什么时候该用它」——这是模型选它的唯一依据
---

# 标题

## 什么时候用
- 具体的触发场景

## 什么时候不要用
- 边界。**这一节比上一节更重要**：没有边界的技能会在不该出现的地方冒出来

## 正文
真正的做法。给命令、给顺序、给理由。
```

**`description` 决定它会不会被想起来。** 写成「数据分析相关」这种，模型永远不知道
什么时候该用；写成「拿到一份没见过的表格数据时先看什么」，它一眼就能判断。

## 名字的规矩（硬的）

**只能用小写字母、数字、连字符**：`soil-eda`、`figure-for-paper`。
中文、空格、下划线都不行——**这个名字会被送进模型的工具/技能清单**，
不合规的名字会让整段对话失败（这个项目为此栽过一次）。

## 放哪儿

| 放哪儿 | 什么时候 | 你能不能直接写 |
|---|---|---|
| `<工作区>/.dawn/skills/<名>/SKILL.md` | 只跟这个课题有关 | **能**，直接 `write` |
| `~/DAWN/skills/<名>/SKILL.md` | 你想在所有项目里都用 | **不能**——它在工作区之外，会被权限门拦下 |

**所以默认写进项目里。** 如果用户说「我以后每个项目都想用」，
就写进项目、然后**明确告诉他一句**：

> 已经写进 `.dawn/skills/soil-eda/`。想让它在所有项目里都生效的话，
> 把这个文件夹挪到 `~/DAWN/skills/` 下——我写不了工作区外面的路径。

**不要自己想办法绕过去**（比如用 bash 的 `cp` 写到外面）——
那条边界是故意的，绕过它就等于它不存在。

## 写完之后

1. 告诉用户**文件在哪**
2. **重启不需要**——技能在每段新对话开始时读一次，所以**下一段对话就生效**；
   当前这一段不会突然多出来一个技能
3. 如果他要改，直接说「改一下那个技能」，你再编辑那个文件
