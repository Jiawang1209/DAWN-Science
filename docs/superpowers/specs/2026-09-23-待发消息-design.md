# 待发消息：排着的话看得见、撤得回、能改插队（学自 Codex）

2026-09-23 · 分支 `queued-messages` · 作者定了「回车默认排队」（选项 A）

## 1. 要解决什么

08-15 起，回复还在跑时输入框就能发（协议 5.6）：回车 = `steer` 插队，Cmd/Ctrl+回车 = `followUp` 排队，
两条都是 pi 原生（`AgentSession.prompt` 的 `streamingBehavior`）。缺的是 Codex 截图里好用的那一半：

1. **排着的话假装已经发出去了。** `writeToSession` 在写的那一刻就 `events.userTurn`——
   转录里立刻出现一条用户发言，位置在 agent 这一轮的中间；而模型真正读到它是几分钟之后。
   人看到的顺序与模型看到的顺序不一样。
2. **排着的话动不了。** 撤不回、改不了、不能把一条「排队」改成「现在插进去」。
3. **回车默认打断。** 回车插队意味着手快一下就改了 agent 正在做的事。

不做：侧边并行会话（另一轮，单独设计）。

## 2. 交互

```
┌ 对话 ───────────────────────────────────────────────┐
│ … agent 正在跑工具 …                                  │
│                                                      │
│ ┌ 待发 · 2 ─────────────────────────────────────────┐ │
│ │ 排队  顺便把 7 月的也算一下            [插队] [撤回] │ │
│ │ 插队  用 30m 网格，别用 10m                  [撤回] │ │
│ └───────────────────────────────────────────────────┘ │
│ ┌ 输入框 ───────────────────────────────────────────┐ │
│ │ 随心输入                                           │ │
│ │ 回车排到这一轮后面 · Cmd/Ctrl+回车插队        [↑] │ │
│ └───────────────────────────────────────────────────┘ │
└──────────────────────────────────────────────────────┘
```

- **忙着时：回车 = 排队（followUp），Cmd/Ctrl+回车 = 插队（steer）。** 与 08-15 对调。
  忙着且框里有字时，发送键的无障碍名从「插队」改成「排队」，提示行文字跟着改。
- **待发条**贴在输入框上方，只在有待发消息时出现。每条一行：标签（`排队` / `插队`）+ 文字（单行截断）
  + 常驻按钮（不是悬停才出现）：
  - **插队**：只在 `排队` 那种上有。把这一条改成 steer——当前工具跑完、下次调模型前就送进去。
  - **撤回**：从队列里拿掉，文字与附图放回输入框（框里已有字时接在后面，中间空一行），人改完可以再发。
- **真送到模型那一刻**，那条从待发条消失，同时出现在转录里——**位置就是模型读到它的位置**。
- **按停止（或 Esc）**：排着的消息一并撤回输入框。停止的意思是「这一轮不做了」，
  排在它后面的话不该在停下之后自己冒出来开一轮新的；也不能丢——放回输入框，人决定还发不发。
  （pi 自己的交互模式也是这么用 `clearQueue()` 的：「restoring to editor when user aborts」。）

## 3. 哪些会话有

**只有 native。** 待发队列是 pi 的；acp / cli / 内核 / pty 没有这回事，行为完全不变：
能力缺席要能被问出来——运行时有没有 `editQueue` 就是判据，后端据此决定走新路还是旧路。

## 4. 分层

依赖决策（规格 §4）：坐在 pi-coding-agent 的 `AgentSession` 上——
①用 `prompt(…, { streamingBehavior })`（已在用）、`clearQueue()`、订阅里的 `queue_update` 事件；
②放弃了 pi 以外自建队列（pi 的队列才是模型真正读的那份，另建一份必然漂移）；
③我们的不变式挂在 native 运行时的**镜像**上：镜像只记 pi 没记的东西（id、原图、我们这边的原文），
顺序与「送到了没有」一律以 pi 的 `queue_update` 为准。

### 4.1 运行时（`src/runtime/native.ts`）

- 每段会话一份镜像 `待发: { id, 文, 图, 送法 }[]`（按 steer / followUp 各自的先后）。
- `write` / `writeWithImages` 多收一个可选的 `queueId`。
  - 忙着（`inFlight > 0`）→ 进镜像，交 pi 排队，emit `{ kind: "queue", items: [{ id, behavior }] }`。
  - 不忙（人按下时还在跑、到这儿刚好跑完了）→ 照常开一轮，并立刻 emit `queue_delivered { id, newTurn: true }`。
- 收到 pi 的 `queue_update`：steer / followUp 两张单子**哪张变短了，就从镜像那张的头上摘掉相应条数**
  （pi 从头送，按文字 `indexOf` 摘第一条），每摘一条 emit `queue_delivered { id, newTurn: false }`，再 emit 一次 `queue`。
  **只认变短、不认变长**：pi 的输入处理是异步的，镜像先进、pi 后到，那一瞬 pi 比镜像短不代表送到了。
- `editQueue(sessionId, id, "remove" | "steer")`：`clearQueue()` 清空 pi 那份，
  按镜像顺序重新送一遍（先 steer 后 followUp；改插队的那条换成 steer）。
  重送走 `送一轮` 同一条路——此时已经不忙的话，第一条开新一轮（`queue_delivered newTurn: true`），其余排在它后面。
  `remove` 返回被拿掉那条的 id。
- 重送时 pi 抛错：那条从镜像拿掉，emit `queue_failed { id, message }`。
- `abort`：先 `clearQueue()`、清空镜像、emit `queue` 空单，返回被撤下的 id 列表。

### 4.2 后端（`src/workbench/backend.ts`）

- `writeToSession` 带 `behavior` 且运行时支持队列时：生成 `queueId`，把 `{ data, images(原路径), 预览 }` 存进
  `待发存根[sessionId]`，**此刻不写 `userTurn`、不 `beginTurn`**。
- 收到 `queue_delivered`：从存根取出，`events.userTurn(data, 预览)`；`newTurn` 为真才 `runRecorder.beginTurn`。
- 收到 `queue`：用存根把 id 翻成 `{ id, text, behavior, images: 预览 }`，交给中枢 `events.setQueued(sessionId, …)`。
- 新操作 `editQueue { sessionId, id, action }` → `{ text, images }`（`remove` 时带回原文与原图路径，`steer` 时空）。
- `abortSession` 的返回多一个 `withdrawn: { text, images }[]`（按原先后）。
- 会话停止 / 退出：清存根。

### 4.3 中枢与协议

- 中枢 `Entry` 多一个 `queued?: QueuedMessage[]`，与 `team` / `kernels` 同一纪律：**整份换掉、进快照、不进转录**
  （转录是「发生过什么」，待发是「还没发生的」）。缺省 = 没有待发。
- 协议：新 update 类型 `queued`，新操作 `editQueue`，`abortSession` 响应加可选 `withdrawn`。协议版本按惯例升一个小号。
- **mock**（硬性准入第 1 条）：`editQueue` 与 `abortSession.withdrawn` 在 `scripts/mock-inference-server.mjs`
  所在的那份假后端里补分支——注意 e2e 真跑的是 native 运行时，假的只是模型，所以 mock 这一侧补的是协议操作的桩。

### 4.4 界面（`src/ui/views.tsx`）

- `排队ref` 语义对调：Cmd/Ctrl 按着 = 插队。
- 待发条组件：读会话快照里的 `queued`；按钮调 `editQueue`；撤回的结果放回输入框（文字接在后面、图并入 `待发图`）。
- 停止 / Esc：`abortSession` 返回的 `withdrawn` 同样放回输入框。

## 5. 失败要出声（规格 7.5）

- `editQueue` 找不到那条（已经送到了——人按下的那一刻 pi 刚好把它送走）：返回 `not_found`，
  界面说「这条刚好已经送出去了」，不静默。
- 重送时 pi 抛错：与现在一样 emit 一行 `[native runtime 错误]`，那条从镜像里拿掉，后端收到 `queue_failed` 把存根里的原文
  推给界面（中枢一条 `notice` + 放回输入框），不丢字。

## 6. 验证

- 单元：运行时镜像的「只认变短」、重排顺序、改插队、abort 撤回；后端存根 → userTurn 的时机。
- e2e（`e2e/busy-gap.spec.ts` 改写，沿用 `sleep 5` 夹具拖住一轮）：
  1. 忙着回车 → 待发条出现一条「排队」，转录里**此刻只有一条**用户发言；这一轮跑完 → 待发条消失、转录两条。
  2. 忙着回车再点「撤回」→ 待发条消失、字回到输入框、转录始终一条。
  3. 忙着回车再点「插队」→ 标签变「插队」，最终照样送到。
  4. Cmd+回车直接是「插队」。
  5. 有待发时按停止 → 字回到输入框。
- 设计契约：新按钮「插队」「撤回」常驻可见（量 `opacity`），不与已有按钮文案互为子串。
- 视觉基线不动（待发条只在忙时出现，十张基线都不在忙态）。

## 7. 审查后改的（2026-09-24）

第一版测试全绿之后，对照 pi 源码逐行审查，抓到五处测试没覆盖到的：

1. **不经界面的写也进了 pi 的单子**（飞书 / 微信不带 `behavior`；界面的「忙」也可能比运行时晚一拍）。
   镜像不收它们，按条数对账就会错位；撤回重送时 `clearQueue()` 把它们一并清掉、再也回不来。
   → 后端给有待发单的会话里**每一句用户的话**都发 `queueId`（不忙时运行时当场报「送到、开新一轮」，
   转录照旧在那一刻写）；运行时镜像**连没身份的也收**，只是不上待发条；全部撤下时没身份的就地出声。
2. **只有图、没字的一条**：pi 按文字摘送到的那条，空文字永远摘不掉。→ 交给 pi 时补一句「（见附图）」。
3. **图片转述那几秒**：此前这几秒里这句话哪儿都看不见，按停止也撤不回来，转述回来还会在停下之后开一轮。
   → 忙着时先进镜像（标「未进 pi」）、上待发条；转述回来还在单上才交给 pi。
4. **关会话时排着的话**：此前存根一删了事，待发条还挂着。→ 撤下、留一句 notice、清掉待发条。
5. **我们以为在跑、pi 说没在跑**（pi 的 `isStreaming` 在 `prompt()` 开头晚立、收尾早放）：
   落在缝里的话 pi 会当新的一轮直接跑，不进单子。→ 先挂在镜像上，这一轮收尾后按新一轮送（插队在此退化为排队）。

另：中止失败时撤下的话留一句 notice；中止时排着的图没带回也说出来。

**已知未修**：以 `/` 开头的消息在 pi 里要先过一道异步的扩展命令检查，重排时它进单子的先后可能晚于镜像，
对账可能把送到记到相邻那条上。概率低、后果是转录里两句顺序对调，留待下一次。
