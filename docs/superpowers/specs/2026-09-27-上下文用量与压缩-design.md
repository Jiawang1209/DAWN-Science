## 1. 要解决什么

作者要的形态是 Claude Code / Codex 那样：**一眼看得见上下文有多满；快满时自动压缩；也能手动 `/compact`；压了，对话里留一条说清压了什么。**

写这份 spec 时对着代码与 pi 0.86 的实现查实了下面几件事（行号是 2026-09-27 `agent-basics` 上的）：

- **a. pi 已经在静默地自动压缩。** `src/runtime/native.ts` 建会话用 `SettingsManager.create(spec.workspace, agentDir)`，没有任何覆盖；
  pi 的 `DEFAULT_COMPACTION_SETTINGS` 是 `{ enabled: true, reserveTokens: 16384, keepRecentTokens: 20000 }`（`pi-coding-agent/dist/core/compaction/compaction.js:76`）。
  上下文过线时 pi 自己调模型写摘要、把早先的消息换成摘要——而 `translate()` 对 `compaction_start` / `compaction_end` 走的是 `default: return`。
  **转录里一个字都没有，模型却忘了细节。** 这违反规格 7.5（失败必须出声、截断要说清省了多少）。`src/` 里 `compact` / `compaction` 一处都没有出现。
- **b. 压缩之后仪表会说旧数。** `contextUsage()` 的 `usedTokens` 来自 `latestUsage()`——倒着扫 `session.state.messages` 找最后一条带用量的消息。
  压缩后 `messages` 换成「摘要 + 最近保留的那几条」，保留的老助手消息身上还带着压缩前的用量，于是面板照旧报压缩前的数。
  pi 自己的 `getContextUsage()` 专门处理了这一点（压缩之后、下一次回复之前给 `tokens: null`）。
- **c. 压缩之后用量会被再报一次（推断，Task 3 用测试证实）。** `emitUsageIfNew()` 按「最后一条带用量的消息在 `messages` 里的下标」判重；
  压缩后数组变短、下标变了，同一份旧用量会再发一次 `turn_usage`，而 `run-recorder.ts` 对 `turn_usage` 是**累加**的（`s.pendingTokens = { input: 攒.input + … }`）——账本重复计。
- **d. 续接时压缩前的对话从界面上消失，且没有任何记号。** `history()` 用的是 `s.sessionManager.buildSessionContext().messages`——那是「模型读的那一份」，
  压缩后以一条 `role: "compactionSummary"` 开头，而 `history()` 不认这个 role、直接跳过。重启之后点开一段压缩过的对话，前面几十轮凭空没了。
- **e. 仪表的数与压缩的判据不是一个数。** 我们报的是 `input + cacheRead`；pi 判线用 `calculateContextTokens(usage)`
  （`usage.totalTokens || input + output + cacheRead + cacheWrite`，`compaction.js:88`）。Anthropic 那类 provider 的 `cacheWrite` 与上一次的 `output` 都在上下文里，
  我们漏了——人看着 80%，pi 按 90% 压了。
- **f. 三处注释过时。** `src/ui/App.tsx` 的 `{/* 上下文用量。**已用 token 尚未采集，面板如实说，不拿字节去凑** */}`、
  `src/ui/panels.tsx` `ContextPanel` 头注「已用了多少 token 目前**尚未采集**」、`src/protocol/operations.ts` `getContextUsage` 注释「`usedTokens` 暂缺」——
  其实 2026-08-10 就接上了（`e2e/context-usage.spec.ts` 断言的就是真数）。
- **g. `run_code` 给模型的文字没有上限。** `src/tools/run-code.ts` 的 `摘要()` 把 stdout / stderr 原样拼起来交给 pi；
  `src/runtime/tool-output.ts` 的 `budgetToolResult` **只管进事件流的那一份**（文件头明写「模型侧的上下文预算不归我们管」）。
  pi 自带的 bash 在工具里自己截（50 KB / 2000 行），`run_code` 没有。图与 HTML 已经不进模型（`摘要()` 只写一句「生成了一张 image/png」），大块文字会。

## 2. 交互

### 2.1 仪表：输入卡附栏右侧，常驻

```
┌ 输入卡 ───────────────────────────────────────────────────────────────┐
│ 今天帮你做些什么？@引用工作区文件，/调用技能与指令                         │
│                                                        [模型 ▾]  [发送] │
├───────────────────────────────────────────────────────────────────────┤
│ [＋] [~/proj] [终端] [优化输入]            [◔ 上下文 37%]  [请求批准 ▾]  │
└───────────────────────────────────────────────────────────────────────┘
```

- 一颗带字的按钮（圆环 + 「上下文 37%」），**不是悬停才出现**。无障碍名就是按钮上的字（不另起一个 aria-label：看到的与读屏听到的是同一句）。
- 百分比 = 已用 / 模型上限。三档颜色（颜色从令牌来，`--dawn-warning` / `--dawn-danger`）：
  - 常态：`已用 < 0.85 × 自动压缩线`
  - 提醒（`data-level="warn"`）：`≥ 0.85 × 自动压缩线`，按钮上多一句「快满了」
  - 过线（`data-level="over"`）：`≥ 自动压缩线`（下一次回复前 pi 会压）
- 按钮上的字随状态变：

| 状态 | 按钮上写 | 弹层里多说的 |
|---|---|---|
| 内置对话，有真数 | `上下文 37%` | `47.2k / 128k tokens` |
| 内置对话，最近一次回复之后又加了东西（工具结果、你刚发的话） | `上下文 约 37%` | 「其中有一截是估的：最近一次回复之后新加的内容按字数估」（pi 不单独报那一截有多大，所以不写数） |
| 内置对话，还没有过回复 | `上下文 —` | 「第一次回复之后才知道——系统提示词与工具说明也占地方，只数对话会少算」 |
| 内置对话，刚压缩过、还没有新回复 | `上下文 已压缩` | 「刚压缩过，等下一次回复才知道现在用了多少」 |
| 模型上限拿不到 | `上下文 12.3k` | 「这个模型没报上限，算不出比例，也不会自动压缩」 |
| ACP / 外部 CLI | `上下文 读不到`（灰） | 「这是外部 agent，它自己管上下文与压缩；DAWN 读不到它用了多少」 |
| 内核 / 终端 | 不画 | — |

### 2.2 手动压缩：`/compact`、弹层按钮、⌘K

- 输入框里整句是 `/compact` 或 `/compact 保留 X 和 Y`（且没附图、没附文件）→ 不当一句话发出去，走压缩；`/compact` 后面那句作为摘要的额外要求交给 pi（`compact(customInstructions)`）。
- **只在内置对话里拦**。ACP / 外部 CLI 那边 `/compact` 原样发给 agent——Claude Code 之类自己认这个命令，我们不替它做、也不吞掉它。
- `/` 菜单最前面多一条「压缩上下文 `/compact`」（D3），只有内置对话显示。选中写 `/compact ` 进草稿，不替人发（与菜单其余项同一规矩）。
- ⌘K 多一条「压缩上下文」。不可用时照样列出，写明原因（没有会话 / 外部 agent / 这一轮还在跑）。
- 三个入口调的是同一个动作（`Actions.compactContext` 与 `onCompact`，一个动作一个家）。

### 2.3 转录里的压缩标记

```
你：……
agent：……
─── ⟲ 已压缩上下文 · 自动：快到上限了 · 112k → 约 9.4k tokens ────────── [这次的摘要]
    早先的对话换成了一段摘要交给模型；上面的记录都还在，模型现在读的是摘要。
    压缩本身用了 输入 98.1k · 输出 1.1k
你：……
```

- 每次压缩**一定**留一条，四种状态各有说法：
  - 正在压：`⟲ 正在压缩上下文…（自动：快到上限了）`——这时算「这一轮在跑」，停止键可用，按了就取消压缩。
  - 压完：如上。「这次的摘要」展开 pi 写的那段摘要原文（按钮不叫「展开 / 收起」：「收起」已经是另一颗按钮的全名，文案互不为子串）（Goal / Progress / … 那个结构）。
  - 没压成：`⚠ 上下文没压缩成：<原因>`（`data-status="failed"`）。pi 的几句英文原因翻成中文（「对话还太短，没有可压缩的」「刚压缩过，还没有新内容」），其余原样透传。
  - 取消了：`上下文压缩停下了，没有改动`（停止键、调整方向都会走到这里）。
- 原因三种：「你让压的」（手动）、「自动：快到上限了」（过线）、「自动：超过了上限，压完重试这一轮」（overflow，pi 会自己重试）。
  从记录里恢复出来的那几条不知道原因（pi 的记录里没存），就不写原因。
- `112k → 约 9.4k`：前者是 pi 算的压缩前用量；后者是压缩后**对话部分**的估值（不含系统提示词与工具说明），所以带「约」，并在下一次回复后由仪表给真数。
- **可见的转录不删任何东西**。模型读的是摘要，人看到的还是完整的来往；标记那一行正是分界。
- 导出对话（markdown）里写一行 `> 上下文已压缩：…`。

### 2.4 续接

重启后点开一段压缩过的对话：**完整的来往都回来，压缩那一处有一条「已压缩上下文」标记**（带摘要，不带原因）。不再只剩压缩后那几轮。

## 3. 哪些会话有

- **native（本机与远端）**：仪表、自动压缩、手动压缩、标记、续接全有。
- **acp / cli**：仪表灰着说读不到（D5）；`/compact` 原样转给 agent；没有「现在压缩」。ACP 的 `usage` 是**整段会话累计花了多少**（`src/runtime/acp/runtime.ts` 里 `段.上次累计` 那段），不是「上下文里现在有多少」，不能拿来凑。
- **kernel / pty**：都不画。

## 4. 分层

依赖决策（规格 §4）：坐在 pi-coding-agent 0.86 的 `AgentSession` 上。

① **用到的导出符号**（全部核对过 `node_modules/@earendil-works/pi-coding-agent/dist/`）：
- `AgentSession.compact(customInstructions?: string): Promise<CompactionResult>`——手动压缩（`agent-session.d.ts`）。它会先 `abort()` 当前这一轮；我们在它前面挡一道忙守卫（D8），所以走到它时不会有一轮在跑。
- `AgentSession.getContextUsage(): ContextUsage | undefined`（`{ tokens: number | null; contextWindow; percent }`，`extensions/types.d.ts`）——仪表的唯一数源。
- 会话事件 `compaction_start { reason }` / `compaction_end { reason, result, aborted, willRetry, errorMessage? }`（`AgentSessionEvent`）——标记的唯一来源，手动与自动同一对。
- `AgentSession.messages`（找最后一次真回复的用量，判断是不是「约」）+ 包根导出的 `calculateContextTokens(usage)`（与 pi 判线同一个函数）。
- `SettingsManager.applyOverrides({ compaction })`（**内存里改，不写文件**）与 `getCompactionSettings(model)`（读出 `reserveTokens` 算自动压缩线）。
- `SessionManager.getBranch()` 与 `CompactionEntry`（`{ type: "compaction", summary, tokensBefore, … }`）——续接时把完整来往与压缩点一起还原。
- 包根导出的 `DEFAULT_MAX_BYTES`（50 KB）——`run_code` 给模型的上限与 pi 的 bash 同一个数。

② **放弃了什么**：
- 不自己写摘要提示词、切点算法、分轮摘要（pi 的 `prepareCompaction` / `findCutPoint` / 结构化摘要格式照用）。
- 不用 `setAutoCompactionEnabled` / `SettingsManager.setCompactionEnabled`——**它们写 pi 的 `settings.json`**（`settings-manager.js` 的 `setCompactionEnabled` 末尾 `this.save()`）。我们的设置不许悄悄落进 pi 的配置文件。
- 不接 `session_before_compact` 扩展钩子（不改 pi 的摘要内容）。
- 不做 tokenizer。「最近一次回复之后新加的」那一截用 pi 的 chars/4 估，**只有那一截**，并在界面上标「约」。
- 不给外部 agent 估一个数。

③ **不变式挂在哪**：
- `NativeRuntime.translate()` 的 `compaction_start` / `compaction_end` 两支：**每次压缩必出一条标记，失败与取消也出**（设计契约扫描盯着这两支在不在）。
- `NativeRuntime.contextUsage()` 只从 `session.getContextUsage()` 取已用数——**仪表上的数与 pi 判线用的是同一族函数**，不再各算各的。
- `NativeRuntime.compact()` 的忙守卫：`inFlight > 0` 就拒。
- `compaction_end` 成功时把 `usageIndexReported` 挪到新下标：**同一份用量不报第二次**。

## 5. 协议（下一个 minor，纯新增）

执行时读 `src/protocol/version.ts` 的 `WORKBENCH_PROTOCOL_VERSION`，major 不变、minor + 1（写 spec 时是 `8.0`，别的计划可能先占了 `8.1`）。

- 新操作 `compactSession { sessionId, instructions? } → {}`（`mutating`，要写权）。非 native → `invalid_request`「只有内置对话能压缩上下文——外部 agent 自己管它的上下文」；忙着 → `conflict`「这一轮还没说完，等它做完或先停止，再压缩上下文」。
  **不等压完**：开始了就返回，结果看转录里那条标记。
- 转录新增 `compaction` 项：`{ id, status: running|done|failed|cancelled, reason?: manual|threshold|overflow, tokensBefore?, tokensAfter?, summary?, error?, retried?: true, usage? }`。
- `getContextUsage` 响应新增三个可选字段：`estimated: true`（已用里有一截是估的）、`afterCompaction: true`（刚压完、还没有新回复；此时不给 `usedTokens`）、`compactAt`（自动压缩线；自动压缩关着时不给）。
  **`usedTokens` 的口径变了**：从「最近一次请求的 `input + cacheRead`」改成「pi 算的当前上下文」（含上一次输出与缓存写入，再加最近回复之后新加的估值）。形状不变，故仍是 minor；版本史里写明。
- **mock 同一次改动补上**（准入规则 1）：假模型认出 pi 的摘要请求（系统提示词带 `context summarization assistant`）回一段固定摘要；
  一句话带「塞满上下文」时报 `prompt_tokens: 120000`，让自动压缩在 `dev:mock` 与 e2e 里都能真的触发。
  另加一个测试旋钮 `DAWN_COMPACT_KEEP_RECENT_TOKENS`（与 `DAWN_LEASE_TTL` 同一个路子）：pi 默认要保留最近 2 万 token，短对话「没有可压缩的」；`dev:mock` 与 e2e 把它设成 1。

## 6. 不做

- 压缩那次调用进账本（D7 的缺口：设置 → 用量会少算这部分；标记上写着花了多少）。
- 自动压缩的开关（D2）。
- 外部 agent 的上下文用量（ACP 将来若有「当前上下文」这一类更新，再接）。
