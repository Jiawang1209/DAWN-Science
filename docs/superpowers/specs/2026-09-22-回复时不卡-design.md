# 回复时不卡 · 设计（分支 `perf-render`）

- **日期**：2026-09-22
- **起因**：Windows 上的朋友说回复时太卡。基线见 `plans/2026-09-22-效率提升-回复时卡顿-基线.md`：
  30 轮历史时每段字重跑 425 个组件（更正后的计数），4× 降速下约 10 帧/秒。
- **作者定的方向**：参考 Codex / Claude / Hermes 这几个不卡的产品去做。

| 产品 | 能读什么 | 读到了什么 |

| **Hermes 桌面版**（MIT，与我们同栈：nanostores + streamdown + use-stick-to-bottom + shiki） | 源码，读设计不复用代码 | 整套做法，见下 |
| **Codex 桌面版**（闭源） | 按 `REFERENCES.md` 第七条只能读 CSS 聚合事实与依赖表，**不读 JS**；而且解包目录已不在本机 | 无 |
| **Claude 桌面版**（闭源） | 同一条边界：依赖表 + CSS | 见第六节 |

**闭源两家的 JS 我们不读**——规格 §3.3（不接触外部非开源代码）。所以「怎么做」主要来自 Hermes；
好在它和我们同一套栈，而且它正是为同一个症状改过的（它的注释原话：*「every token got its own React commit + Streamdown markdown re-parse」*）。

### Hermes 的做法（事实，路径相对 `hermes-agent-main/apps/desktop/`）

1. **攒一攒再写**：字先进一个缓冲，**至多 33ms 写一次**到 store（`use-message-stream/index.ts:178-225`，理由在 `utils.ts:59-67`：16ms 时每个 token 一次提交）。
   回合结束 / 要人回答这类「状态翻转」立即写，不等。
2. **只换正在写的那一条**，其余消息对象身份不变（`index.ts:108-116`）。
3. **整份消息数组只有一个小组件订阅**（`chat/index.tsx:182-254`），外面的聊天壳**不订阅**（`:299-305`，注释 `PERF: ChatView must not subscribe to $messages`），
   壳只读两个派生的小 atom（「空不空」「最后一条是不是人说的」）。
4. **行 `memo`**；按消息对象缓存转换结果（`WeakMap`）；传给行的回调是稳定的。
5. **markdown**：streamdown 自己按块切、写完的块不重渲；Hermes 另外关掉 `parseIncompleteMarkdown`、只修最后一块
   （`lib/remend-tail.ts`，注释：整段修复占 50KB+ 消息流式脚本时间的约 18%），外面套 `useDeferredValue`，
   **代码块在流式期间不高亮**，写完再高亮。
6. **不做虚拟列表**：只渲染最近约 300 段，更早的「显示更早」（`thread/list.tsx:36-43`）——理由是虚拟列表会和贴底滚动打架。
7. 它也有自己的测量脚手架与记录（`scripts/profile-typing-lag.md`）。

## 二、我们的病灶（对照上表）

| Hermes 的第几条 | 我们现在 | 位置 |
|---|---|---|
| 1 攒一攒 | 每个 item 更新立即 `$items.set`；约 340 段字 → 800–1150 次提交 | `state/transcript.ts:34` `upsertItem` |
| 2 只换一条 | **已经是**（`next[i] = item`，其余身份不变） | 同上 |
| 3 壳不订阅 | **最顶层 `App` 订阅整份 `$items`**，侧栏、坞、顶栏全陪跑（空对话 111 个） | `App.tsx:264` |
| 4 行 memo | `src/ui` **零 memo**；行的回调、`generated`、`cases` 每次都是新对象 | `views.tsx:4372-4410` |
| 5 markdown | `parseIncompleteMarkdown` 整段修；流式中照样高亮 | `markdown.tsx:162-171` |
| 6 预算 | 全部渲染 | — |

## 三、改法（分四步，每步量一次）

**第 1 步 · 攒一攒**：`upsertItem` 对「同一条、还没写完」的更新合并，**至多 33ms 落一次**；
新增条目、写完（`final`）、`dropItem`、快照、换会话**先把缓冲冲掉再立即落**——顺序不能乱、最后一个字不能晚到。

**第 2 步 · 壳不订阅**：`App` 不再 `useStore($items)`：
- `busy` → 派生 atom `$回合进行中`（布尔，一轮只翻两次）；
- 笔记本 cell 清单 → 派生 atom，cell 没变时保持同一个数组；
- 事件处理里要读的（`是空的`）→ `$items.get()`；
- `ConversationView` 自己订阅 `$items`（它本来就要），`App` 不再往下传 `items`。

**第 3 步 · 行 memo**：`TranscriptRow` 包 `memo`，比较器看 `item` 身份与几个标量；
回调走「稳定引用 + ref 取最新」；`generated` / `cases` 按内容比（元素身份逐个比），不按对象比。
**结果**：写完的历史消息在流式期间一次都不重跑。

**第 4 步 · markdown 尾巴**（先量，第 1–3 步之后仍卡才做）：`useDeferredValue` 包流式正文；流式期间代码块不高亮。

**不做**：虚拟列表（Hermes 明说它和贴底滚动打架，而我们 09-16 刚在贴底上踩过坑）；「只渲染最近 N 段」等量完再说。

## 四、判据

- 同一剧本（`npm run perf:streaming`），`PERF_LABEL=改后`，对着基线两张表比。
- 目标：30 轮历史时**每次提交重跑从 425 降到几十**；4× 降速下帧率 **≥ 30 帧/秒**；一段字对应的提交数 ≤ 1。
- 全套 e2e + 视觉基线照旧全绿（规则 ③），`dev:mock` 人肉看一眼流式是否顺、最后一个字是否按时到。
- 新增一条可判定规则进 `tests/ui/design-contract.test.ts`（规则 ②）：**`App.tsx` 里不许出现 `useStore($items)`**。

## 五、风险

- **攒一攒会让最后一个字晚到**：`final` 必须立即冲。e2e 里所有「等回复出现」的用例会替我们盯着。
- **memo 比较器写错 = 该变的不变**（比如产物条不出现、案例卡片不更新）。比较器只放「身份比」，不做聪明的判断；有专门单测。
- `ConversationView` 本身还很大（含输入框），第 2 步之后它仍按 33ms 重跑——量了再看要不要把转录列表再拆出去。

## 六、Claude 桌面版（闭源，依赖表 + CSS）

只读了 `package.json` 与构建出的 CSS，没打开任何 JS。
- 聊天界面是本地预编译的网页包（`Contents/Resources/ion-dist/`，在 asar 之外），**没有 package.json**，依赖读不到；
  外壳的 package.json 里没有状态库、markdown 渲染库、虚拟列表库、高亮库。
- CSS：高亮是 highlight.js 系（`.hljs` 41 处），排版是 Tailwind Typography（`.prose` 223 处）。
- **markdown 容器的每个直接子块 `content-visibility: auto`**，按元素类型给占位高度（标题 1.5rem 到 div/pre/table 16rem），
  只在支持 `overflow-anchor` 时启用；块容器 `contain: layout`。**它没用 JS 虚拟列表，靠 CSS 让屏幕外的块不排版。**

## 七、结果（2026-09-22）

三步都做了、各自提交：`a7a0660`（第 1、2 步）、`0aca7e4`（第 3 步）。第 4 步（markdown 尾巴）没做——量下来 JS 已不是瓶颈。

### 重画（更正后的计数，同一剧本）

| 历史轮数 | 每次提交重跑：改前 → 改后 | 一次回复共重跑：改前 → 改后 | 提交次数：改前 → 改后 |
|---:|---:|---:|---:|
| 0 | 77 → **21** | 88,708 → 9,361 | 1159 → 438 |

历史消息的 `Streamdown` 在流式期间**不再重渲染**（改后只剩正在写的那一条）。

### 帧（CPU 降速 4×；改后跑了 3 遍，写中位数与范围）

| 历史轮数 | 改前 | 改后 |
|---:|---:|---:|
| 1 | 19 帧/秒 | **116**（115–116） |
| 11 | 11 帧/秒 | **83**（83–93） |
| 31 | 10 帧/秒 | **29**（28–78） |

1× 下改前改后都在 120 帧/秒附近（这台 Mac 本来就不卡）。

### 没达到的与没做的

- **31 轮 + 4× 仍只有约 29 帧/秒**，目标 30 擦边，而且三遍之间飘得厉害（28–78）。
  JS 这时几乎不随历史涨了（每次提交 44 个），涨的是浏览器给整页长文重算样式与布局。
- **试过 Claude 的 `content-visibility: auto`（每个 markdown 块）**，各跑 3 遍：31 轮时中位数 29 → 50 帧/秒，
  **但 11 轮时 83 → 62**——几百个小块各自的可见性判断本身有代价。形状也有风险：我们没有一处 portal，
  浮层都长在行里，包含块一变 `position: fixed` 的浮层就会被关进块里（`backdrop-filter` 那次踩过同一个坑）。
  **这一轮不上**，留作下一轮的候选：要么只包「写完的整条消息」并先把行里的浮层挪到 portal，要么学 Hermes 只渲染最近 N 段。
- 提交次数仍是约 400（按 33ms 算应是 170 左右）——还有别的东西在每次落字后再提交一次，没查。
- 名字压缩过的 `U` 仍随历史线性涨（30 轮时每次提交约 14 个），没查是谁。

## 八、第二轮（2026-09-23）：查清两个疑点 + 只渲染最近若干条

### 先把名字看清

`npx vite build --minify false` 出一份不压缩的界面，再跑同一个剧本，并让计数器**按「这次提交重跑了哪几个」归类**
（`提交的花样`）。两个疑点当场有答案：

1. **多出来的提交不是我们打的。** 30 轮历史那一处 400 次提交里，我们自己的只有约 107 次
   （花样是 `ConversationView+TranscriptRowImpl+…`，正对应 5.6 秒 ÷ 33ms）。其余是库自己的：
   `MarkdownCode`（shiki 高亮异步回来再刷一次）约 41 次、markdown 表格块约 9 次、`StickToBottom` 约 10 次、
   还有 20 次**空提交**（什么都没重跑）。
2. **随历史变长的那个是 `TurnNavigator`**（左缘刻度尺，一轮一颗 `Button`）与 `SessionUsage`（顶上那条账）。
   两个都吃整份 `items`，于是每落一次字把整列刻度重画一遍——30 轮时每次提交约 14 颗 `Button`。

### 改了三处

- **`TurnNavigator` 包 `memo`**，比较器只看**用户那几轮的 id 与文字**：模型在写的是 agent 那条，它就不动。
- **`SessionUsage` 包 `memo`**，比较器只看轮数 / 工具的起止 / `usage`——**一个字都不看正文**。
- **只渲染最近 40 个转录块**（`src/ui/transcript-budget.ts`，学自 Hermes 的 render budget）：
  更早的不进 DOM；转录顶上常驻一行「更早的 N 条没有显示」+「显示更早的 40 条」/「全部显示」；
  换会话回到默认。**刻度尺点到预算之外的那一轮时，先把它放出来再滚**——否则就是「点了没反应」。

### 结果（同一剧本，帧数据各跑 3 遍）

| | 第一轮之后 | 第二轮之后 |
|---|---:|---:|
| 30 轮历史 · 每次提交重跑 | 44 | **36** |
| 30 轮历史 · 一次回复的提交数 | 约 400 | **113**（1×） |
| 31 轮历史 · 树里组件总数 | 15,421 | **9,455** |
| 11 轮 + 4× · 帧/秒 | 83（83–93） | **93**（87–99） |
| 31 轮 + 4× · 帧/秒 | 29（28–78） | **45**（43–89） |

**目标达成**：4× 降速下 31 轮历史 ≥ 30 帧/秒。与最初的基线相比：10 帧/秒 → 45 帧/秒，每次提交重跑 425 → 36。

### 仍然留着的

- **飘**：31 轮 + 4× 三遍是 43 / 45 / 89，中位数 45。这台机器上的噪声就这么大，结论只看中位数。
- 空提交（约 20 次）与 shiki 异步高亮的提交没有动。真要再省，Hermes 那招是**流式期间代码块先不高亮**，写完再高亮。
- `content-visibility` 仍未上（理由见上一节）。预算这一刀已经把它想解决的那部分吃掉了大半。
