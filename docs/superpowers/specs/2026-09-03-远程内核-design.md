# 远程内核（C 档）—— 设计

> 2026-09-03 · 分支 `remote-kernel` · 主线「数据分析平台」第三轮
> 前置：`plans/2026-08-11-phase2b-remote-workspace.md` §1.1（三档远端执行）、`spikes/FINDINGS.md` Spike F（2026-08-11 真机实测）

## 一句话

远端会话里 `run_code` 在服务器上**你自己装好的** ipykernel / IRkernel 里跑：内核进程在服务器上起，
五个 zeromq 端口经 SSH 隧道回本地，`kernel/channel.ts` 那套通道、笔记本格、变量面板、内核型环境快照
**原样复用**。服务器上我们不装、不传任何东西。

## 它补的是什么

- 2026-08-27 起远端会话**不挂 `run_code`**（代码会在本机跑、文件在服务器上，静默错位），笔记本格写着「远端会话的内核还没做」。
  「产物」「笔记本」两轮的东西在作者最常用的场景（连着计算节点分析数据）里都是灰的。
- 路线图 S15「ExecutionContext」在 ②-B 被改成 B 档（远端工作区）时明写「C 档不作废，等真需要交互式画图时是纯增量」。现在就是那时候。
- Spike F 已证明：zeromq 在 SSH 隧道上跑的是原样 TCP，`enchannel` 那条链路不知道中间隔着 SSH，**不需要第二套协议**。

## 前提（作者约束，2026-08-20：服务器只有 sshd，内核那条多要一个 Python）

- 服务器上要有**用户自己装好的** ipykernel（Python）/ IRkernel（R）。我们不装、不建议装到哪、不上传任何文件。
- 内核起来时**自己**在它的 `$TMPDIR`（缺省 `/tmp`）写一份 connection.json；收摊时我们删掉它。这是内核的文件，不是我们放的。
- `ssh2` 的分层决策不变（②-B 计划 §4）：`Client` 的 `exec` / `forwardOut` / `sftp` 三样。**本轮第一次真用 `forwardOut`**，它早在决策范围内。

## 形状

| 层 | 东西 | 在哪 |
|---|---|---|
| 隧道 | `隧道(client, 远端端口)` → 本地 `net.Server` 监听 `127.0.0.1:0`，每个入站 socket 开一条 `forwardOut("127.0.0.1", 0, "127.0.0.1", 远端端口)` 对接。一个内核五条；`关()` 关 server 与所有在途通道 | 新 `src/remote/tunnel.ts` |
| 远端起停 | `起远端内核(executor, {语言, 解释器路径, cwd, 文件名})`：`setsid nohup <cmd> -f "$f" </dev/null >"$f.log" 2>&1 & echo DAWNPID=$!`（`setsid` 有才用：不用的话执行器超时/中止会连内核一起杀；`</dev/null` 免得内核抱着 SSH 通道的 stdin）；轮询读文件（最多 60 次 × 500 ms），**文件内容走 base64 `DAWNJSON=` 键值**回来——不按位置、不找花括号，MOTD 里有 `{` 也不怕；返回 `{pid, 文件, 连接信息, setsid}`。`停远端内核`：`kill -TERM`，轮询 `kill -0` 且 `ps -o stat=` 不是 `Z` 才算活着，最多 10 s 后 `kill -9`；然后 `rm -f <文件> <文件>.log`。扫残留的 glob 与 `pkill` 模式都要 `[d]awn-…`（wrapper shell 自己的命令行也含这段文字，否则会把自己杀掉） | 新 `src/remote/kernel-launch.ts` |
| 通道 | `channel.ts` 加第二个入口 **`attachKernelChannel({连接信息, 进程})`**：连接信息里的端口是**本地**端口（隧道那头），`进程 = {pid, kill}` 由调用方给（`kill` 走 SSH）。`launchKernelChannel` 内部改成「spawn 得到连接信息与进程 → 调 `attachKernelChannel`」，本机那条路行为不变。**`spawnteract` / `enchannel` / `@nteract/messaging` 仍只此一文件碰**（`tests/source-hygiene.test.ts` 那条不动） | `src/kernel/channel.ts` |
| 运行时 | `KernelRuntime.start(spec)`：`spec.remote` 有值就走远端起法（起内核 → 五条隧道 → `attachKernelChannel`），`stop` 反向收摊。`native.ts` 那句 `this.opts.kernels && !spec.remote` 拿掉 `!spec.remote` | `src/runtime/kernel.ts`、`src/runtime/native.ts` |
| 挂载 | `挂载.ts` 的 `interpreterOf(语言)` 变成 `interpreterOf(对话, 语言)`：远端会话答这台服务器的配置；`sessionDirOf` 不变 | `src/kernel/挂载.ts` |
| 探测 | **复用 `src/kernel/probe.ts`**：`枚举候选` 用远端的 `platform` / `home` / `env`（登录 shell 里 `printf` 出来），`探测命令` 每条经 `executor.exec` 跑（登录 shell，并发 4、8 s 超时），`解析探测` 不动。远端 `which -a` 的输出与本机同一条解析 | `src/remote/interpreters.ts`（薄，只做「在远端执行」） |
| 配置 | `remote_connections` 加两列 `python_path` / `r_path`（可空；`hasColumn` 迁移，与 `sessions` 加列同一模式） | `src/store/schema.ts`、`src/store/connections.ts` |
| 协议 | `probeInterpreters` 加可选 `connectionId`（有就探那台服务器）；新增 `setRemoteInterpreter { connectionId, language, path: string \| null }`；`listConnections` 的记录多 `interpreters: { python?: string; r?: string }`；`getEnvironment` 的 kernel 分支多可选 `where`；推送多一条 `remoteList: "changed"`（名单变了，界面重拉）。协议 7.29 → 7.30。~~`kernel_state` 事件带 `where`~~——一段会话要么整段远端要么本机，笔记本格拿会话自己的 `remote.label` 就够 | `src/protocol/` |
| 快照 | 内核型环境快照多一个**可选** `where: { connectionId }`（与 shell 型同名同形）。**本机内核不带它，指纹一个字节不变**（老行不裂）。远端内核指纹含它：同一个 conda env 搬到另一台机器，是另一份快照 | `src/env/snapshot.ts`、`src/kernel/environment.ts` |
| 界面 | 笔记本格：远端会话不再整格说「还没做」，改为下文那张选择器 / 正常 cell 流；头部胶囊标 `Python · <服务器名> · <状态>`（本机仍是 `Python · <状态>`）；cell 行与转录里的输出只标语言——面板本身就是按会话的，胶囊已经说了在哪台。设置里服务器编辑行加 Python / R 两格 + 「探测」（复用 `InterpreterPicker`） | `src/ui/notebook.tsx`、`src/ui/remote.tsx`、`src/ui/App.tsx` |
| mock | `fake-ssh` 认三件事：探测脚本（答一份候选清单，其中一条是 e2e 夹具里的**真** python）；起内核命令（**真在本机 spawn** `<python> -m ipykernel_launcher -f <本机 tmp 文件>`，`cat` 读真文件，`DAWNPID` 是真 pid）；`forwardOut` 直接 `net.connect` 到本机端口；`kill` 真杀。假的只有「另一端是谁」，与现有尺度一致 | `src/remote/fake-ssh.ts` |

**ExecutionContext 不建新表。** 「在哪跑」这个事实已经有落点：会话的 `connection_id`、shell 快照的 `where`、本轮内核快照的 `where`。
加一张表是为了还不存在的消费者造概念——路线图 ③ 前的反向约束（「只产出事实，不需知道谁会消费」）不许。

## 定案

1. **解释器：接口 + 探测 + 唯一则用、多个则问、零个则说**（作者 2026-09-03 定）。
   - 每台服务器各配一份路径，落在 `remote_connections`。本机路径在服务器上没有意义。
   - 第一次 `run_code` 时没配 → 探测。**唯一**一个装了 ipykernel 的：用它，转录里说一句「这台服务器用的是 `<路径>`」，**写进配置**（下次不探、设置里看得见）。**多个**：笔记本格列出来让人点，工具回给模型「找到 N 个候选，已在笔记本格列出，请等用户选定后再试」（不选择、不重试）。**零个**：如实说「这台服务器上没有装了 ipykernel 的 Python」，给 `KERNEL_PACKAGE` 那句装法，工具回错，`run_code` 仍挂着（下次装好了就能用）。
   - agent 不参与选择（它选错了不出声）；但工具描述里写明当前用的是哪个解释器、内核 cwd 在哪。
2. **内核 cwd = 起它那一刻会话的远端当前目录**，转录里那句「内核已在 `<目录>` 起来」带上；之后 agent `cd` 内核不跟（与本机一样，内核不跟 bash 的 cd）。
3. **断线 = 内核死**（作者定，2026-09-03）。连接进 `disconnected` → 这台服务器名下的内核全部标 `exited`，转录一句「与服务器断开，Python 内核里的变量已经不在了」；正在跑的那段 Run 记 `terminal_reason: disconnected`（**不是 failed**，我们不知道它跑完没有）。不重连、不接回。人重新连上后，下一次 `run_code` 懒起一台新的。
4. **不留残留，只杀自己的。** 文件名 `dawn-<装机id>-<语言>-<时间戳>.json`，装机 id 是首启时生成、存在 settings 里的随机串。每次连接就绪后先扫 `$TMPDIR/dawn-<装机id>-*.json`，`pgrep -f '[d]awn-<装机id>-'` 杀掉、删文件（pgrep 模式带方括号，Spike F 纪律 3）。两台电脑共用一个服务器账号时互不误杀。内核状态里记 pid 与文件路径——以后做「接回」是纯增量。
5. **`run_code` 与本机一样不过权限门。** 门的判据是 shell 命令的形状，判不了 Python；每个 cell 问一句会把笔记本废掉。这与权限规格定案 5「不是沙箱」是同一条边界，那行灰字加半句「`run_code` 里的代码在远端同样不拦」。
6. **图默认留在对话里**（内核接进对话·定案 6 不变）。agent 明确要保存时写到远端工作区的 `figures/`——那是用户的目录，不算往服务器放我们的文件。
7. **Spike F 四条纪律全部落进实现**：①一律登录 shell（`RemoteExecutor.exec` 已是）；②一切输出走 `键=值` 正则，连 connection.json 也 base64 成一个键值（不做任何位置解析）；③ `pgrep` 模式带方括号；④杀进程等它真没了、僵尸不算活着。
8. **失败出声**：起不来走 `diagnoseLaunch` 同一套三种实情（没这个程序 / 程序在但包缺失 / 起来了但握手超时），远端 stderr 尾巴走 `cat <日志>` 取回——日志文件与 connection.json 同名加 `.log`，收摊一起删。隧道建不起来（`forwardOut` 报错，常见于 sshd 关了 `AllowTcpForwarding`）单独一句话说清是哪一层。
9. **不借**：远端 Jupyter Server（第二套协议，Spike F 已否决）、把内核跑在 Slurm 作业里、多台服务器同一内核、断线接回。
10. **远端内核猝死（OOM、被集群杀）本地察觉不到**——本机内核有进程 exit 事件，远端没有；只有挂载层「静默 5 分钟」那道兜底与下一次执行时的报错。知情的欠账，真撞上再加心跳。
11. **扫残留先于起内核**：每次连上后的扫残留是异步的，而它的 `pkill` 会命中本装机刚起的那台；所以起内核前要等这一台服务器的扫残留结束（装配层 `扫过` 表）。
12. **装配层没接远端时，远端会话不挂 `run_code`、`runInKernel` 也拒**（`能起远端()`）——宁可没有工具，也不给一个在错误机器上跑的工具。
13. **`dev:mock` 缺省用假服务器**（`DAWN_FAKE_SSH=1`，可用 `DAWN_FAKE_SSH=0` 关掉）：准入规则 1 要 mock 与 e2e 共用一份假后端，此前 dev:mock 从没设过它。

```
标签 [genek      ]  主机 [genek.example.org]  端口 [22]  用户 [liu]

```

两处用的是同一个 `InterpreterPicker`（三态：探测中 / 候选列表 / 缺包只给装法）。

## 事件与记账

- 起内核：转录一条系统行「正在在 genek 上起 Python 内核」→「内核已在 `/data/proj` 起来（`/home/liu/.../python`）」；起失败一条红字，带三种实情之一。
- 每段执行一条 Run（`execute_python` / `execute_r`，沿用），`environment_snapshot_id` 指向带 `where` 的内核快照。
- 断线：`kernel_state` 推 `exited`，原因 `disconnected`；正在跑的 Run 收 `disconnected`。

## 验证

- **单测**：隧道（假 client：入站即 `forwardOut`、关 server 时在途通道全关）；起停（假 executor：`DAWNPID` 取值、MOTD 夹在 JSON 前 / 中 / 后三种、僵尸判定、`kill -9` 兜底、日志尾巴取回）；扫残留（只杀自己装机 id 的）；探测三条路（唯一 / 多个 / 零个）各自的转录句与配置写入；断线 → 内核标死 + Run `disconnected`；快照 `where` 进指纹、本机指纹不变（拿 R5 之前的固定样例断言逐字节相等）；协议 7.30 兼容表。
- **e2e**（真内核 + 假 SSH）：远端会话里 `run_code` 出数、出图、cell 头标着服务器名；未配置时笔记本格列出候选、点一条后能跑；设置里探测 + 选定落库；断线后转录有那句话且再连后能再起。
- **视觉基线**：笔记本格与服务器编辑行都不在十张里，不重存。
- **真机**：作者集群上 Python 跑一次（起、出图、变量面板、停后 `pgrep` 为空）。**R 远端没验过**——Spike F 只测了 Python，IRkernel 那条路径按同一形状做，规格与历史里如实标「未经真机验证」。
- **mock**：`npm run dev:mock` 里假服务器能起真内核，与 e2e 同一份 `fake-ssh`（准入规则 1）。
