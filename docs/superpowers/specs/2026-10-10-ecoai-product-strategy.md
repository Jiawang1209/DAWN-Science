# EcoAI-Science 独立桌面产品方案

日期：2026-10-10。状态：产品组织建议与迁移计划，尚未创建 EcoAI 项目或更改应用代码。

## 用户最新意图

EcoAI 初期是和 DAWN 一样的桌面产品，以当前 DAWN 的代码和功能为基础；希望放进单独的项目文件夹，作为独立产品开发。以后再考虑接入单位平台和网页化。

因此采用“可追溯派生的独立项目”作为本计划方向：独立目录、独立 Git 仓库、独立应用身份与发布周期。前一轮提出的单仓库双品牌构建保留为比较方案，不作为默认执行方案。

**建议保留 DAWN，复制其 Git 版本形成 EcoAI，随后分别开发。** 不把 DAWN 原文件夹改名或搬空，不用运行时切主题来充当独立产品。EcoAI 沿用科研工作台能力，再逐步加单位入口和生态领域默认内容。

## 为什么值得做，代价在哪里

若单位将以自己的品牌持续部署、宣传、维护，并需要平台接口和独立发布，建立独立产品有实际价值。初版功能与 DAWN 相同完全可以，品牌与维护主体本身就能形成分发边界，不必为了区分名字立即造一批新功能。

仅为一次宣讲改 logo 时收益较小；但用户已经提出后续单位平台建设，这使独立产品成为合理的准备方向。单独文件夹的成本不高，长期成本主要来自两个版本的通用修复、依赖升级、兼容性和发布验证。

| 项目组织方式 | 初期工作 | 长期维护 | 本次选择 |
| --- | --- | --- | --- |
| 单仓库两品牌配置 | 最省同步成本 | 发布/权限仍在同一仓库 | 前一轮建议，现不作为默认 |
| 独立目录与仓库，保留派生历史 | 保留代码基线并分离应用身份 | 选择性同步通用改动，需要纪律 | 采用此方向 |
| 独立仓库加共享核心包 | 首期需要抽取稳定接口 | 团队扩大后可降低重复维护 | 共性边界稳定后再评估 |
| 复制源码、删除历史、各自随意改 | 复制很快 | 难追踪来源与修复，分叉成本高 | 不建议 |

## 独立安装所需的工程分离

当前源码已核对到：electron-builder 的 `appId= science.dawn.app`，桌面配置/数据库/凭证依赖 Electron userData，默认工作区在 `~/DAWN/workspace`，首启迁移会尝试从旧 Electron 目录迁入，更新默认源指向 DAWN GitHub Releases。

因此改名至少要同步这些边界：

1. 名称、图标、安装程序/可执行文件、桌面菜单、托盘、通知、关于与帮助。
2. 应用标识、单实例锁与协议注册，确保两程序能同时安装和运行。
3. 在任何 CONFIG/DB/日志/凭证路径求值之前确定 EcoAI userData 与 sessionData；数据库、浏览器 Local Storage、缓存、更新状态与凭证交接不能串到 DAWN。Electron 支持设置应用名称与数据路径，路径初始化必须早于依赖它的读取。[Electron app 文档](https://www.electronjs.org/docs/latest/api/app)
4. 默认工作区、scratch、全局 skills/memories、CLI_HOME 等逐项检查；不能只改 userData 就宣称所有目录隔离。由用户显式选中的同一个科研项目可共用文件，但两个产品不能自动共用隐私配置与默认会话数据库。
5. EcoAI 首次启动默认空数据，不触发 DAWN 的旧 Electron 数据迁移。不自动导入模型密钥、SSH 配置或会话；用户以后明确要求导入时再做可预览的迁移工具。
6. 更新源、安装目标、包名识别、下载/交接状态都要只认 EcoAI。没有独立更新端点时明确关闭检查并说明“尚未配置”，不能回落 DAWN 更新源。
7. CLI 和 E2E/dev:mock 也带各自隔离路径；兼容的内部 `dawn` 文件格式/协议不做无意义全局替换。

## 两个项目如何并行维护

- 共同起点记录在 EcoAI 的 `docs/UPSTREAM.md`：源仓库、完整提交 SHA、版本、派生日期、同步规则。
- 通用 Bug/兼容性修复优先在 DAWN 修复并验证，再在 EcoAI 的同步分支 cherry-pick；每次在 EcoAI 运行相应测试，不假设来源通过就本产品通过。
- 机构接入、单位文案、专属默认值在 EcoAI 开发。EcoAI 发现的通用修复单独提交，便于反向移植到 DAWN。
- 不让公共修复和品牌定制混在同一个巨大提交；不对两个仓库做自动双向合并或目录覆盖。
- 每个产品单独记录已集成的源提交、自己的版本和发布验证。两者初期可以功能一致，也可以错开发版。
- 一个批次做完界面刷新后再同步比逐个 CSS 提交来回同步更清楚。将来同步频率和冲突成本明显上升时，再评估共享包或上游专用分支。

## 网页化的边界

网页平台适合以后作为 EcoAI 的新客户端/部署形态。可复用协议概念、科研运行能力和部分 UI；桌面版仍可保留。

浏览器没有本机 Electron IPC、任意文件访问和本机终端权限。网页化前需要确定账户与授权、工作区归属、服务端计算任务、用户隔离、文件上传/存储和凭证保管，再设计网络传输适配；不能把本机特权 API 原样暴露为公开 HTTP 服务。

本轮不提前建设这些系统，也不承诺只改构建参数就能完成网页升级。

## 许可与单位归属的发布前事项

当前 package.json 声明 AGPL-3.0-or-later。换名字和仓库不会自动改变代码许可；单位版的署名、分发许可和以后网络版本的对应源码安排应基于现有许可及实际代码权属确定。AGPL §13 对修改后的程序通过网络交互设有源码提供条款，不能据此简单推断单位所有平台或科研数据都要公开。[GNU AGPL 正文](https://www.gnu.org/licenses/agpl-3.0.en.html)

正式命名、Logo、域名/appId、仓库归属、签名主体与更新托管地址在单位发行时确定。这些不会阻碍先完成本地 UI 设计与隔离迁移准备。
