# DAWN 产品维护与渐进迭代计划

> 执行者使用 `superpowers:executing-plans` 在当前会话内逐项推进；默认单线执行，不委派子 Agent。本文确定维护顺序、边界和验收门；具体功能项先根据现有实现形成独立规格与执行计划，不把本表当成可跳过设计的代码清单。

**Goal:** 尽量保留当前功能与操作习惯，以小批次补齐运行诊断、任务续接、项目进展、产物来源和长期维护；一项验收及本地 main 合并结束后，才启动下一项。

**Architecture:** 复用现有设置、对话、概览、路线、Bot、产物与恢复机制。优先只读检查、明确提示和用户主动触发的补充操作；确需改变既有行为时，先展示具体差异与兼容方案。

**Tech Stack:** 现有 TypeScript、React、Electron、Vitest、Playwright，以及本地 Python/R；默认不新增依赖、数据库结构或协议操作。

**规划基线:** 2026-10-20，`main` 为 `f439189954a7c9a3211c00a66398767f816dbb7b`，版本 `0.0.33`。这是规划时的代码身份，不是当日功能测试通过证明。

## 1. 与长期路线图的关系

沿用 [长期路线图](2026-10-04-长期开发路线图.md) 的不变式、证据要求和长期方向。本文是用户在 2026-10-20 确认的维护顺序：先做局部现状核实，再依次处理六个方向；不要求先完成旧 P0 的全部五个参考任务，也不据此把旧 P0–P6 标成已完成。

本轮暂缓科研质量基准，不需要用户提供标准科研案例，不运行模型排行榜或科研打分。错误路径、临时目录、缺失依赖和中断状态可以使用可控工程场景验收。

六个方向是维护队列，各方向内的小批次分别设计、测试和合并。单项已满足验收时登记“已核实，无需改动”，不为完成清单重复建设。

## 2. 保留现有功能的约束

1. 保持左侧项目/会话、中间对话、右侧可开关坞的三栏布局，以及现有入口、名称、快捷键和默认操作。
2. 保留前五项升级：子 Agent 资源与界面、科研审查规则、分析路线、Bot 协作、整理交付与结果解读；每项维护说明可能影响哪些已有路径。
3. 优先复用已有状态、协议、检测与预览；不顺带大规模重构、换框架、升级依赖或统一重写旧模块。
4. 不自动安装包、切换解释器、重启/清空内核、重复运行分析或重放文件写入；需要这些操作时显示具体对象、影响及主动操作入口。
5. 已有会话、项目、原始数据、产物与用户修改保持可用。修复缺陷若必须改变行为，明确列出触发条件、前后差异及回归判据；涉及操作习惯、数据格式或权限变化时先收敛并确认该子项设计。
6. 不推送、不发布、不替换已安装的软件。不因为编译或测试通过就宣称科研判断正确。

## 3. 单项推进与合并规则

每次只允许一个维护子项进行中，顺序如下：

1. 从当时实际 `main` 核实相关功能、已有修改和已知问题，给本项留下简短基线。保留与本项无关的修改及预览资料。
2. 写明本项解决的问题、保持的行为、允许改动的文件范围、验收场景和不覆盖的情形；较大方向先拆最小子项。
3. 在 `codex/` 独立分支和工作树中实施；缺陷先复现，再做最小修复，不把新需求混进修复。
4. 运行有判别力的定向测试。新增协议同步补共享 mock；修改用户主路径补实际 Electron 验收；UI 变化查看实际预览，确认原入口仍可使用。
5. 功能子项收口执行类型检查、全量 Vitest、构建与相关 Electron 回归；纯文档子项只检查内容、链接和 diff，不为文档改动重复跑功能套件。
6. 核对改动范围、回归结果、原功能兼容性、未解决问题，更新单项验收报告、本文台账和开发历史。测试失败或关键证据缺失时不合并、不开始下一项。
7. 用户本次已授权按该流程逐项本地提交并合并 main；通过上述条件且在既定范围内时，不重复询问同一合并许可。涉及新增操作方式等范围变化，先处理第2节第5条的设计确认。
8. 主目录干净且具备快进关系时使用 `git merge --ff-only`；不自动 pull、push、覆盖用户修改或把冲突强行解决。合并后检查实际 HEAD、工作区状态并复验本项关键路径；若合并后的检查失败，先处理该项，禁止继续下一项。
9. 报告提交、验证、限制及下一子项。保留必要的独立工作树、案例和预览，不自动清理用户证据。

功能子项收口命令（在当前工作树中运行，构建完成后再执行相关 E2E）：

```bash
npm run typecheck
npm test
npm run build
git diff --check
```

E2E 文件必须在具体子项计划中按本项范围列明；M0核实与M1首批的候选命令如下，启动时再次确认用例与实际改动对应：

```bash
npx playwright test e2e/first-run-default.spec.ts e2e/provider-test.spec.ts e2e/environment.spec.ts
```

本文件不安排一次运行全部 Electron 或视觉基线。失败时查看日志及差异，不自动更新截图基线。工作树测试结果不能冒充合并后结果；快进未改变功能源码时，合并后复跑本项关键用例，无需无原因重复完整套件。

## 4. 维护队列

| 顺序 | 方向 | 最小首批范围 | 保持的现有行为 | 验收核心 |
|---|---|---|---|---|
| M0 | 局部基线与保护清单 | 核实首项相关实现，记录代码身份、现有入口及定向检查 | 不改产品行为，不要求完成全部旧 P0 | 能区分已有能力、已复现缺陷和计划建议 |
| M1 | 运行诊断与故障处理 | 核对现有检测；按用户反馈首批仅补解释器保存错误的原位提示 | 原功能与布局保留，不增加诊断区、检查流程或自动安装 | 原位错误准确，修正后撤下，原检测与模型服务可用 |
| M2 | 中断后的任务续接 | 先统一本地中断事实与已保存产物的展示；进一步续接另拆一批 | 不自动重放已产生副作用的操作，保留现有恢复机制 | 区分已完成、仍运行、失败和未知，重启不重复写入 |
| M3 | 项目进展与上下文留存 | 在现有概览入口汇集可确认的目标、进展、文件和下一步 | 不改三栏，不自动把生成摘要写成已确认研究条件 | 重开能定位进展，切换项目不串内容，摘要来源可检查 |
| M4 | 产物版本与来源 | 先为明确登记的关键产物补数据/脚本/运行引用和覆盖提示 | 保留现有产物预览、整理交付和独立验证；不擅自移动原件 | 缺失来源明确，已有交付可打开，同名覆盖后版本不混淆 |
| M5 | 多 Agent 执行控制 | 先审计共享内核、同名输出与取消行为，按已复现冲突补保护 | 不重写团队协议或取消现有协作，不复制大型原始数据 | 同时执行及失败/取消时，另一任务与用户文件不受污染 |
| M6 | 发布、性能与反馈 | 分批维护支持说明、长对话性能和主动导出的诊断资料 | 不自行发布或换安装版，不默认上传日志、路径或聊天 | 文档有证据，性能按原预算，诊断可检查且脱敏 |
