## 已复现并修复

1. **P1 后台排队交接缺失未被发现**：后台开始时已保存快照，但尚无 meta.json；排队期间删除 handoff.json 后，原实现竟然完成无背景任务。失败测试保存于本轮证据。修复为在 mailbox 入队前，将 SHA-256 绑定到同一个持久化子任务身份；缺失或冲突在启动前失败，子进程启动次数为 0。
2. **P2 未启用交接的选择没有冻结**：首次普通委派未交接，重复工具调用仍可追加父历史。现在 null 表示明确不继承、undefined 表示旧记录未绑定；持久化中同时冻结启用和未启用，不通过重试改变选择。旧无交接记录仍可继续。
3. **P1 退出漏等活跃普通子任务**：Workbench 的优雅退出判断只覆盖终端、内核、传输，漏掉统一编排中的子任务。真实装配门闩测试先红，现已将 queued/running/stopping 的编排工作纳入退出判断；仍用原 1500ms 有界收尾及 4000ms 外层兜底，不增加等待预算。真实 Electron 的慢 bash 子任务在重启前变为 cancelled，meta 已终结，原进程树退出，交接字节保持不变。

持久化指纹同时与 meta 核对；同父会话的另一份快照及其 meta 被一起错放过来，也不会覆盖当前子身份的绑定。meta 和快照同时遗失后，从编排状态恢复仍能识别缺失，拒绝重新取材。

最终逐项复核再补两个恢复边界并验证先红后绿：没有任何子绑定的孤立 handoff.json 不会自动成为新任务背景；meta 缺少旧标记、但编排中已有可靠指纹时，重试从持久化绑定修复标记，不误写成 null，也不重新抓取父历史。

旧任务若已有执行或权限冻结事实，即使 meta 缺失，也默认不继承；不能因为旧字段缺失而在重试时扩大历史范围。新任务仍可在首次准备时显式启用交接。

保存的原 trace 显示：业务断言已结束，约 38062ms 进入 Close context，38066ms 打印 Debugger ending，97954ms 触发 fixture 60 秒关闭预算，未出现 Close context 完成事件。原失败没有应用退出事件和进程样本，不能据此区分 inspector/transport、应用 will-quit 或 stdio 持有，不能事后断言为某个单一原因。

本轮在修复前对原后台用例进行 20 次带应用级退出诊断的重复，全部通过；这不证明原问题已经修复。源码检查了本机 Playwright 1.62 的 Electron 自定义关闭链（app.quit 的 Runtime 调用、node connection close、等待 child close、browser context close）及 DAWN will-quit 资源收尾链。

上游也报告过 `app.close()` 在业务通过后卡住的情况：[Playwright #10840](https://github.com/microsoft/playwright/issues/10840)。它使用旧版本和另一运行环境，仅作调查线索，不能据此认定本机故障相同，也没有更改 Playwright 依赖或跳过其 close。

补上**默认被动关闭观察**：每个 E2E fixture 在自己的输出目录保存 child exit/close 与管道状态；仅卡住 5 秒才采集进程树/样本。应用级 evaluate 注入仍需显式开关，默认不注入、不延长预算、不强杀、不吞关闭错误。两个观察器回归先红后绿，检查 watchdog 与正常退出结果。

## 回归中发现的旧测试等待问题

首轮 Node/UI 全量中，方案卡“批准后再次改一改”失败。测试只等待 onAnswer 被调用，就寻找尚未由 Promise.then 恢复的按钮；用延迟的首轮回调能稳定复现。修正测试为等待首轮回调完成和按钮恢复可用，保留未改/改后正文两项原断言，并增加处理中按钮不可用的断言。没有修改产品方案卡实现、延长超时或降低断言标准。

另一轮同时运行全量单元、桌面重复与完整评测时，11 阶段科研批量修正场景在第 11 步仍执行中撞上 25 秒等待上限；前 10 步状态与数值正确，保留原输出，不把它算通过。后续完整集合单独以 4 worker 运行，未修改其 25 秒断言预算或场景。

受限并发首轮另遇旧 MCP HTTP 启动 hook 的 5 秒超时。原 hook 先预留后释放端口、再启动进程，且既不累计 stderr 分块也不监听提前退出，失败时没有足够记录，不能事后认定是哪一种原因。本轮改为子服务器直接绑定端口 0，报告实际端口，累计解码后的 stderr，并立即报告 error/exit；5 秒预算和原有所有客户端断言保留。新增的动态端口启动路径先红后绿，32 项客户端回归通过；MCP 产品客户端未改。
