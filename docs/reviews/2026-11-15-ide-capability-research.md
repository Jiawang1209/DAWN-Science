## 对 DAWN 的结论

当前 DAWN 具有 AI 对话、终端、文件浏览与预览、变更审阅、共享 R/Python 内核及 Notebook 交互入口，但尚未形成以项目源码文件为中心的 IDE 编辑工作区。

“能执行代码”和“有 IDE”需要分开：已有运行内核、终端、文件树可以为 IDE 提供基础，但源码编辑、文件保存和文档状态管理需要明确的用户操作与数据模型。

| 能力 | 当前源码所见 |
| --- | --- |
| AI 对话与执行 | 已有对话、工具执行、文件产出与执行记录。 |
| 终端 | 已有终端工作区与会话管理；终端输入编辑不等同于源码文件编辑。 |
| 文件浏览 | 已有本地/远端目录导航、搜索、预览与复制路径。 |
| 脚本预览 | `src/ui/script-preview.tsx` 明确为只读预览，通过 Shiki 上色，主体是 `pre/code`。 |

| Notebook 运行接线 | `src/ui/App.tsx` 的 Notebook `onRun` 调用 `runInKernel`，导出调用 `exportNotebook`；native 对话与 Notebook 共享会话内核。 |

## Notebook 的边界

当前 Notebook 可以输入并执行代码，展示历史代码和结果；这不等于已经具备任意 `.ipynb` 文档的完整打开、编辑、保存功能，也不等于项目 `.py`/`.R` 文件的源码编辑器。

README 对 cell 有“re-runnable, editable”的较强描述；本次检查到的 Notebook 历史条目渲染和面板参数中没有逐个 cell 的编辑/重跑入口。判断当前用户界面能力应以实际接线为准，不能单靠该段描述将它视为完整 Notebook 文档编辑器。

## IDE 差距的关键判据

对“用户能否亲自管理并修改项目代码”而言，首先要看源码文件能否打开、修改和保存，多个文件能否保持独立的编辑状态，外部变化能否与未保存内容协调，以及执行结果能否对应到所编辑的代码。代码补全、定义跳转、格式化和断点调试是进一步的编辑/调试能力。

本次仅记录现状和能力边界，没有决定新增编辑区的位置、选用的编辑器组件或实施范围。

## 登录后“代码者”工作区观察

用户登录后明确要求继续查看代码编辑和运行工作区。本次查看了“会话”和“代码者”两种视图，打开了查找、会话代码来源选择及全屏菜单，读取了可见按钮说明和编辑器配置。未创建对话、输入或保存代码、提交 AI 请求、启动解释器、运行任务、重启环境、安装包或上传文件。

### 实际布局

根据浏览器实际截图，而非可访问性树的节点顺序：

- 左侧为会话导航。
- 中央为脚本编辑区，下方为控制台和单行执行输入。
- 右上为环境与变量，右下为文件与结果分类区。
- 有分隔线调节各区大小，并提供两种全屏入口。

### 可直接确认的交互与配置

- 存在独立“代码者”页签，而非对话中的代码展示卡片。
- 页面使用 CodeMirror 编辑器，配置 `readOnly: false`；行号、括号匹配和折叠均已启用。保存、运行、查找/替换等快捷键有编辑器接线。
- 查找按钮实际打开了编辑器内的查找框，界面还提示支持正则查找。
- 有脚本页签、新建与保存按钮；未命名页签带修改标记，底部明确显示未保存草稿状态。
- 语言选择器提供 R、Python、Bash、JavaScript。这只证明界面提供了选项，本次未验证各语言的运行实现。
- “从会话选择代码”实际打开来源面板及搜索框；当前账号没有会话，面板显示没有可选的完整代码。
- “收进对话”按钮说明支持将全部代码或选中的片段送回对话。
- 文件与结果区按脚本、数据、图表、报告、临时文件及 AI 说明等分类。
- 脚本页签说明分别表达未保存、当前草稿与元信息状态、尚无关联执行记录和依赖/环境未核验，未把这些不同状态混成一个“完成”。

### 仅观察到入口或说明，未执行验证

- 运行按钮说明：有选区时只运行选区，否则运行当前代码，使用会话的常驻解释器并保留变量。
- 控制台提供单行执行、变量刷新和解释器重启入口；当前显示尚无解释器。
- AI 局部改写按钮说明：先选中代码并给出要求，再预览修改差异、确认应用。本次没有调用 AI，也未验证生成或应用修改。
- 存在整理分析流程入口，但未点击可能触发生成的动作。
- 多文件保存、草稿恢复、文件冲突处理、运行速度、稳定性、结果与代码版本的绑定效果、语言补全及断点调试，均未完成实际验证。

## 值得 DAWN 借鉴的方向

| 观察到的设计 | 对 DAWN 的价值与接入方向 |
| --- | --- |
| 文件型编辑器、脚本页签和明确的草稿状态 | 补齐“打开文件—手动修改—保存”的缺口；区分只读预览、未命名草稿和已保存文件。 |
| 编辑、控制台、变量和结果同屏 | 现有能力在 DAWN 中分散于文件、Notebook、概览和产物等入口；代码工作区可让人连续完成查看、修改、运行和检查。 |
| 选中代码运行及整段运行共用持久解释器 | 复用 DAWN 已有会话 R/Python 内核、`runInKernel`、中断和输出记录，减少在编辑器与 Notebook 输入框之间复制代码。 |
| 对话代码进入编辑器、编辑器选区回到对话 | 连接 AI 生成与人工修改；回传时应保留来源文件与选区，避免仅发送无来源代码片段。 |
| AI 局部改写先预览差异再应用 | 把 AI 协作缩小到明确的选区和变更，允许用户核对修改；与 DAWN 已有变更审阅和溯源能力衔接。 |
| 草稿、执行记录和环境核验状态分别表达 | 将 DAWN 的现有执行记录、代码来源、环境和结果证据放到编辑位置；避免把旧结果误认为当前草稿已经运行。 |
| 文件与结果分类入口紧邻编辑区 | 复用 DAWN 文件、产物和预览模块，减少寻找输入文件、输出图件和报告的跳转。 |

建议的优先顺序是能力层面的判断，并非已批准的实施计划：先补源码编辑/保存、选区与整段运行、控制台与变量查看；再衔接对话选区及 AI 差异修改；之后按需求增加语言服务、格式化或调试。

现有 DAWN 的内核、终端、文件、结果预览与执行记录可以继续复用。源码文件是编辑对象，内核中的变量是运行状态，两者需要分别表达；不能把脚本编辑器直接当成另一份 Notebook，也不能假设 Bash 与 R/Python 使用相同的执行通道。

结论：该站已展示轻量科研 IDE 的交互形态；最值得借鉴的是以可编辑代码为中心的操作连续性。对运行与保存的真实可靠性，本次没有足够证据下结论。
