# DAWN Science 长期开发路线图

> 给后续执行者：本文是长期排序与验收契约，不是跨模块一次性施工单。逐阶段采用 `superpowers:executing-plans`；只有用户明确要求委派时才使用子 agent。先读本文的进度表，再读当前阶段计划。每项功能在实现前完成独立设计、确认和执行计划。

**Goal:** 将 DAWN 从功能较完整的早期科研工作台，推进为可稳定安装、可恢复任务、可审阅结果、可重现分析的桌面科研产品。

**Architecture:** 保留 Electron、pi、SQLite、Jupyter 内核与 SSH 的现有边界。在既有 Run、环境快照、文件事实和事件协议上增量建设，先稳定主路径，再连接科研证据，随后增强恢复与隔离，最后扩展科研生态。

**Tech Stack:** TypeScript / Node.js、Electron、React / Vite、pi、SQLite、Jupyter / ipykernel / IRkernel、MCP、Vitest、Playwright。

- 状态：路线图已建立；尚未执行阶段验收；尚未开始功能实现。

## 1. 方向与范围

核心使用过程：研究人员给出问题和数据，DAWN 帮助形成方案、执行分析、生成结果；研究人员能检查过程、修正步骤，并在另一会话或环境中重新生成结果。

优先保障 R/Python、Notebook、本地文件与 SSH 科研工作区。代码开发是辅助能力，多智能体是可选能力。对 Hermes 学习经验积累，对 Codex 学习隔离与交接，对 Claude 学习文件交付与连接器体验；不以复制三家的功能数量为目标。

考虑过三条路线：全面补齐通用助手功能、先完成科研产品闭环、先重构底层。选择科研闭环路线：先处理阻碍日常使用的问题，再交付结果证据和重跑能力；仅重构被当前任务触及且妨碍验收的边界。

本轮长期路线不承诺自建云端推理、账号同步、移动应用或 Web 版。语音、浮窗、皮肤和记忆图谱列入候选池，只有真实任务证明它们优先于主链路后才进入阶段。原始数据不可被自动清理；远端和供应方数据遵循同一规则。

## 4. 排序与依赖

主顺序：**P0 → P1 → P2 → P3 → P4 → P5 → P6**。

每阶段先交付一个可用切片，再扩大覆盖。P2 最小来源链跑通后可进入 P3，无需先完成所有展示；P1 的 Windows 真机、签名凭证等外部条件可以明确登记为阻塞项，不阻碍已验证主平台上的 P2。P6 扩大公开支持范围前必须回收相关发布欠账。

时间以“已验收任务数”和阶段门推进，不设未经估算的月度承诺。完成 P0 后按实际缺口估算近期阶段；远期每阶段启动时重估。

## 5. 阶段与交付

### P0 · 当前基线和验收入口

目标：让后续开发从真实、可复查的状态出发。

- [ ] **P0-1 能力台账**：逐项关联规格、代码、测试、实际使用证据，区分已实现、已验证、部分支持、未验证、未实现。
- [ ] **P0-2 五个参考任务**：本地表格分析、R 科研绘图、SSH 长任务、既有 Office 文件修改、并行代码任务。使用确定性合成数据，保留输入、预期结果和人工验收表。
- [ ] **P0-3 当日检查基线**：类型检查、单测、构建、相关 Electron 主路径；标注 mock 与真实模型/内核的区别。
- [ ] **P0-4 文档对齐**：修正 README 过时状态，建立支持矩阵和已知问题入口。

**G0 验收门**：五个任务有输入与判据；每个能力状态可定位证据；缺口有任务 ID；没有引用旧测试数量充当当日通过结果。交付台账和基线报告，不以全部任务已通过为 P0 的前提。

### P1 · 安装、运行和发布主路径稳定

目标：新用户在明确支持的平台上走通首次安装到结果保存。

- [ ] **P1-1 首次启动诊断**：区分未配置、配置已保存、鉴权失败、模型不支持、连接失败和实际请求成功；接通解释器探测及缺失依赖提示。
- [ ] **P1-2 环境与内核语义**：明确 Python/R 路径、依赖、工作目录、会话共享范围与重启影响；配置变动不静默复用错误环境。
- [ ] **P1-3 运行时能力矩阵**：API、Claude ACP、Codex ACP 对方案、用量、取消、远端和工具权限逐项显示真实支持。
- [ ] **P1-4 CI 与故障定位**：基于新日志复现 Linux 问题；保存超时诊断；建立稳定的主路径回归入口，不改变既有“测试与发布分开”的策略，除非另行确认。
- [ ] **P1-5 安装包与更新验证**：在隔离配置下测试安装包、旧版升级、失败恢复、凭证交接；签名和平台真机条件独立登记。

**G1 验收门**：已声明支持的平台走通安装→配置→分析→保存→重开；取消和失败能看见原因；升级不丢配置与会话。发布阻塞条件必须写明，未经真机验证的平台不得宣传为已支持。

### P2 · 科研结果的来源、版本与重跑

目标：从一张图或一份表追到输入、代码、参数、环境和执行记录。

- [ ] **P2-1 最小来源契约**：复用 Run 与环境表，定义输入身份、版本、执行引用、输出身份和链路缺失原因；先设计迁移及旧记录兼容。
- [ ] **P2-2 输入与产物版本**：首先覆盖明确读取的本地文件、`run_code` 与已知文件工具；大文件采用预算化身份计算，标注完整哈希或弱指纹；远端读取失败不编造来源。
- [ ] **P2-3 可检查的分析步骤**：关联 cell/脚本、参数、随机种子、过滤规则、模型与评估；代码推断与研究人员确认分开记录，不能靠模型补不存在的实验信息。
- [ ] **P2-4 产物来源视图和版本对比**：展示对应运行、输入和环境；同路径覆盖保留版本关系；找不到旧字节时明确不可恢复，不假装已有历史副本。
- [ ] **P2-5 最小证据包与重跑**：导出 manifest、可分享的代码、环境描述及检验值；默认排除凭证与原始私有数据；在新目录/新内核显式重跑。

**G2 验收门**：P0 的 Python 和 R 任务均能从结果定位最小来源链；输入改变会产生可识别的新版本；全新内核重跑得到预期结果。确定性结果精确比较，数值结果使用预先固定的容差，图像同时检查数据和渲染。缺失链路可见；“链路完整”不等于“科学结论正确”。

### P3 · 长任务恢复、定时任务与运行时交接

目标：任务中断后知道已完成什么，并能安全选择后续动作。

- [ ] **P3-1 恢复契约**：区分模型流、工具执行、内核执行、外部进程与远端任务；分别定义已完成、仍运行、失败、未知和需要确认。
- [ ] **P3-2 可恢复执行点**：从已落盘且可验证的步骤恢复；非幂等动作不自动重试；未知状态先检查再继续。
- [ ] **P3-3 定时运行恢复**：保留 occurrence 去重，处理宿主退出、睡眠和漏跑；只有取得可核验执行状态才改写旧失败处理。
- [ ] **P3-4 API / ACP 交接包**：携带用户目标、已验证结果、文件与内核引用、待办和权限；用户可检查；能力降级可见。交接不伪造原运行时历史。
- [ ] **P3-5 状态与通知**：断线、恢复、完成、失败、待操作由真实运行状态驱动；未变化的监控默认静默。

**G3 验收门**：分别注入应用退出、模型断线、SSH 断线、内核退出和睡眠；不重复写入已完成输出，不把未知运行宣称完成。远端进程重连恢复与内核重启后的重跑分别验收。

### P4 · 并行隔离、审阅与独立核验

目标：并行任务的改动可归属，验证能发现真实错误。

- [ ] **P4-1 Git 工作任务隔离**：独立 worktree、任务绑定、可恢复归档、变更审阅；不自动合并用户分支。
- [ ] **P4-2 科研任务隔离**：输出目录、运行身份、内核租约或串行规则；大型数据只读引用，不为每个 agent 复制一份。
- [ ] **P4-3 归属与回退**：区分用户修改和 agent 修改；联合文件回退与内核状态提示，不能把文件回退描述为变量回退。
- [ ] **P4-4 独立验证路径**：验证输入和实现输入分别管理；reviewer 根据结果文件与外部判据检验；不把另一段模型赞同作为证据。

**G4 验收门**：两个任务同时修改同名目标也能独立审阅；用户手改被保留；失败任务不会污染另一任务；植入的数值、过滤和代码错误能被独立判据检出。

### P5 · 科研工作流、连接器和经验积累

目标：围绕真实科研任务降低重复配置和交付成本。

- [ ] **P5-1 两个完整领域工作流**：先做表格统计/生态分析、文献图形复现；各含示例数据、前提条件、执行、审阅、证据和导出。
- [ ] **P5-2 一个科研连接器闭环**：候选为 Zotero、公开数据仓库或对象存储，按真实用户任务选择一个；实现安装/配置、认证、只读检索、错误提示和撤销连接，再决定写操作。
- [ ] **P5-3 记忆和技能质量管理**：记录来源任务、适用条件、版本、使用、修订和失效；沿用确认制；项目隔离不泄漏私有上下文。
- [ ] **P5-4 单 agent / 多 agent 对照**：固定同一批任务、模型条件与判据，比较正确率、缺陷检出、误报、耗时、费用和用户介入次数。
- [ ] **P5-5 Office 真实交付**：保留既有 DOCX/PPTX 结构、样式及表格公式；检查导出文件，交付可编辑结果与渲染检查证据。

**G5 验收门**：两条领域工作流由全新项目完成；连接器认证失败和撤销有效；技能来源可查看且不跨项目泄漏；多 agent 收益只按实测报告。

### P6 · 发布收口和持续维护

目标：已验证的能力形成外部用户能理解、安装和反馈的产品。

- [ ] **P6-1 支持矩阵与发布清单**：收回 P1 的签名、真机和更新欠账；平台能力依据实际证据声明。
- [ ] **P6-2 迁移与恢复**：升级、数据备份、迁移失败、安装回退与数据库兼容有明确策略；不把旧二进制与新数据库随意组合。
- [ ] **P6-3 使用文档与演示**：使用真实科研案例，说明能做什么、环境前提和结果边界；文档引用当期发布版本。
- [ ] **P6-4 用户反馈闭环**：收集可复现问题和经用户检查的脱敏诊断；不默认上传原始数据、路径、密钥或聊天全文。

**G6 验收门**：每个宣布支持的平台有当期安装与升级证据；五个参考任务有当前结果；阻塞项、发布说明和产品文档一致。

## 6. 跨阶段验收规则

1. mock 测试验证协议和交互；真实内核、真实文件、真实安装包验证执行与交付。真实模型任务另记服务商、模型、日期和输入，不假定输出可逐字复现。
2. 运行记录区分工具退出码、用户目标验收、溯源完整、可重跑和科学正确性；不存在一个笼统的“测试通过”包办五项结论。
3. 每个修复先复现；按变化运行定向测试。改协议同批补 mock；改主路径同批补真实 Electron 验证；可判定设计规则补契约测试。
4. 阶段收口执行 `npm run typecheck`、`npm test`、`npm run build` 和相关 E2E。广泛变更或发布再跑全量 E2E；不得反复无目的跑全套。
5. 性能沿用现有预算入口；先核实 `e2e/performance-budget.ts` 和 `e2e/streaming.perf.ts` 的当前判据，不重新发明一套指标。
6. 数据库与协议变更先设计旧数据兼容、迁移失败处理、恢复步骤及上限；原数据不做破坏性改写。

## 7. 一步一步开发的执行约定

每轮只推动一个任务或一个可独立验收的子任务；默认一条实现主线。用户临时提出 bug 时登记插入原因，修完回到当前任务，不丢原路线。

流程：读取当前状态 → 核实代码 → 明确这一轮交付 → 独立规格/执行计划 → 获得适用的设计确认 → 实现 → 验证 → 审查 → 更新证据和进度 → 报告下一项。

本路线图授权排序和文档建设，不替代各阶段具体设计确认，也不授权后台自动运行。默认不自动 commit、merge、push 或发布；这些动作沿用用户当轮明确授权。已在会话中确认的事项不重复询问。

实现分支使用 `codex/` 前缀；需要隔离时检查并复用合适 worktree。保护已有工作区修改，尤其 `.omc/project-memory.json`；不得为获得干净状态清掉它们。

每项“完成”须同时拥有：代码或文档交付、相应验收证据、变更历史、已知限制。不允许用代码已写完代替任务验收。外部条件受阻时说明可继续的范围，并保留阻塞项。

## 9. 重排规则

每过一个阶段门，或发现会影响数据安全、结果正确性、主路径可用性的故障时，复查排序。竞品的新功能只作为候选证据，不能自动改变优先级。

新增需求记录用户场景、收益、依赖、验收方法和机会成本。修改方向时在本文追加日期与理由，保留已完成证据；不要把历史计划改写成一直如此。

第一阶段完成后，以同一台账持续推进。后续会话可直接说“按长期计划继续”，执行者先定位当前任务及未收口证据，再开展这一轮工作。
