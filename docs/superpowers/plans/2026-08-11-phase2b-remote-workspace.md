# ②-B · 远端工作区

> 2026-08-11 立。取代路线图 §5 里 S15 的原表述 —— 理由见 §1。

## 1. 这一阶段到底做什么

作者的原话：

> *「我的本地是一个 dawn agent，我想通过 ssh 连接远端的服务器，
> 然后使用 agent 在远程服务器里面帮我编程，处理数据，写代码，分析数据。」*

**agent 跑在本地，手伸到远端。** 会话的工作区在那台机器上，agent 的四个工具
（读 / 写 / 改 / 跑命令）全部打到远端执行。

### 1.1 这与路线图原来写的不是一回事

路线图 S15 写的是「ExecutionContext 探测与管理（本地 / WSL / SSH / GPU）」，
而 ②-A 的整套（结构化 Console、变量面板、环境快照）建在 **Jupyter 内核**上，
所以「远端执行」被默认读成了「远端内核」——那要求远端装 `ipykernel`。

作者问了一句要命的话：

> *「为什么一定要有 ipykernel 呢，因为我就是远程登陆服务器而已。」*

**他是对的。** 三档远端执行，代价差得很远：

| | 远端要什么 | 得到 | 失去 |
|---|---|---|---|
| A · 远程终端 | 只要有 shell | 人自己敲 | agent 不参与 |
| **B · 远端工作区（本阶段）** | **只要有 shell** | agent 在远端编程/跑数据；退出码、产出、Run 记账都有 | 图/变量面板这类结构化输出 |
| C · 远程内核 | **要 ipykernel** | 持久会话、图、变量内省 | 远端必须能装东西 |

**共享集群不给装东西是常态**（作者那台教学机连 `pip` 都没有）。
B 的远端依赖是**零**，覆盖「跑脚本、跑流程、写代码、分析数据」——正是作者说的那件事。

**C 不作废**：Spike F 已证明它可行且不需要第二套协议（见 `spikes/FINDINGS.md`），
等真的需要交互式画图时再开，那时是纯增量。

### 1.2 判据（G4 重述）

> 同一段代码在**本地**与**一台真实 SSH 服务器**上各跑一次，
> 两条 Run 记录都可查，且**各自带一份如实标注类型的环境快照**。

「如实标注类型」是新加的：shell 上下文没有内核，它的快照与内核快照
**记的不是同一组事实**，不得共用一个名字假装相同（§3.4）。

## 2. 接缝在哪 —— 为什么这件事可做

`src/runtime/native.ts` 的 `gatedTools()` 把 pi 的四个内置工具**定义**包了一层
（授权门 + 溯源探针），再经 `createAgentSession({ noTools: "builtin", customTools })`
交给 pi。也就是说：

- **工具的 schema 与名字是 pi 的**（模型看到的东西不变）
- **真正干活的那一句是 `original(...)`** —— pi 的本地实现

**换执行后端 = 换掉那一句**，pi 不用动，模型也察觉不到差别。
这正是 Spike A-2 当初选「包装工具定义」而不是「pi 的文件扩展」换来的余地。

## 3. 任务分解

### R1 · SSH 执行器（`src/remote/`）

- 一条**长连接**，多路复用 exec channel；文件读写走 SFTP
- **所有命令走登录 shell（`bash -lc`）**——理由见 §3.1
- 断线：如实进入 `disconnected`，**不静默重连**（§3.3）
- 单元测试用一个假 SSH 端口；真机验证走 e2e 之外的一条手动脚本（同 Spike F）

### R2 · 远端工具后端

四个工具换成 SSH 版本，**名字与 schema 一字不改**：

| 工具 | 本地 | 远端 |
|---|---|---|
| `read` | fs.readFile | SFTP read |
| `write` / `edit` | fs.writeFile | SFTP write |
| `bash` | 本地子进程 | `bash -lc` over SSH，**带退出码** |

`ProvenanceProbe` 同步改造：它现在按本地路径 `stat`，远端要按远端路径。

### R3 · 远端工作区的表示

- 项目的 `workspace` 需要能表达「哪台机器上的哪个目录」
- **不在路径里编码主机**（`ssh://user@host/path` 这种）——那会让每一处
  路径处理都要先解析一次，而漏掉一处的表现是**在本地机器上按远端路径去读**
- 改为：项目记录多一个可选的 `host` 引用；`workspace` 仍是那台机器上的绝对路径

### R4 · 凭证

- SSH 密码 / 私钥口令进 **OS 钥匙串**，与模型 key 同一套（`CredentialStore`）
- **配置文件里只留主机、端口、用户名、私钥路径**——那些不是秘密
- 认证顺序：私钥 → ssh-agent → 密码（Spike F 已验三种都通）

### R5 · 环境快照（shell 型）

- 记：主机名、发行版、内核版本、CPU/内存、PATH 上的 `python`/`R`/`git` 版本、
  工作区是不是 git 仓库
- **与内核快照分成两种类型**，各自说清自己是什么（§3.4）
- 沿用 S17 的两条禁令：不回头探测；环境变量只记键不记值

### R6 · 终端接到远端

dock 里的终端连到那台机器（`A` 档顺带就有了）——同一条 SSH 连接，
不额外开一条。

### R7 · 文件浏览器看远端

`listDirectory` / `readFile` 走 SFTP。**路径守卫照旧**：
远端工作区之外的路径一样拒绝。

## 3.1 四条来自 Spike F 的硬纪律（都要落进实现）

1. **远端执行必须走登录 shell。** ssh2 的 `exec` 是非登录非交互 shell，
   不读 `~/.bashrc`。后果不是「跑不了」，而是**看到的是另一台机器**——
   作者装好的 `ipykernel` 在 spike 眼里不存在。
   **环境快照记的必须是「人自己 ssh 上去看到的那套」。**
2. **远端 stdout 不只有你要的东西，且顺序没有保证**（MOTD 与 stdout 交错）。
   凡要解析的输出，一律 `键=值` 正则或最外层花括号，不靠行号也不靠标记。
   *一个假「通过」比一个失败危险。*
3. **`pgrep` 会匹配到执行它的那条命令行本身**（用 `[i]pattern` 躲开）。
4. **杀进程要等它真的没了，僵尸不算活着。**

## 3.2 授权门在远端更要紧

本地跑错一条命令，代价是你自己的工作区；**在共享集群上跑错，代价是别人的**。
所以远端会话的能力白名单**默认更窄**：`fs_write` 与 `exec` 必须显式给，
且门的拒绝理由要指名「这是远端」。

## 3.3 断线：不静默重连

一条 SSH 断了，**正在跑的那条命令的结果就是不知道**——它可能跑完了、
可能没跑完。此时：

- 会话进 `disconnected`，界面如实说
- **不自动重跑**：重跑一条可能已经执行过的命令，比不跑危险得多
- Run 记录标 `terminal_reason: disconnected`，**不是 failed**——我们不知道它失败没有

## 3.4 两种环境快照，不共用一个名字

内核快照记的是「这个解释器里有什么」；shell 快照记的是「这台机器是什么」。
**它们不可比**。按项目的命名纪律（路线图 §1.4），
状态词只能声称我们真正验证过的东西——所以是两个类型，各自带 `kind`。

## 4. 依赖分层决策：`ssh2`

按规格 §4，依赖决策必须写明三件事：

1. **坐在哪一层**：`ssh2` 的 `Client`（连接、`exec`、`forwardOut`）与
   `sftp` 子系统。**只用这三样**，不用它的服务端、不用它的 SFTP 服务实现。
2. **放弃了什么**：不自己实现 SSH 传输层与认证（那是密码学，自己写等于自造漏洞）；
   代价是 ssh2 的行为差异我们要跟着（例如它**不读 `~/.ssh/config`**——
   所以主机信息必须显式配置，见 R4）。
3. **不变式挂在哪个钩子上**：
   - 不变式 3（没有不可见的行动）→ 每条远端命令都经 R2 的包装器，
     与本地走同一个 Run 记账口
   - 不变式 5（声明层 / 事实层分离）→ 远端产出仍从 **git 事实**算
     （`git -C <ws> status --porcelain` over SSH），不听 agent 声明

**Spike F 已验**：三种认证、端口转发、SFTP 之外的 exec 通路都可用。

## 5. 风险

| # | 风险 | 触发信号 | 应对 |
|---|---|---|---|
| RW1 | **每次工具调用一个 RTT**，一轮几十次调用会明显变慢 | 一轮 > 30 秒 | 文件读写批量化（SFTP 一次多个）；`bash` 合并成一条脚本 |
| RW2 | 远端工作区不是 git 仓库 → 产出永远「无法确定」 | 变更 pane 常年空 | 建会话时就检测并明说，而不是等到看不见产出才发现 |
| RW3 | 共享集群有资源限制（进程数、内存、超时） | 命令被 kill | 退出码与信号如实上报，**不重试** |
| RW4 | 断线频繁 | 会话反复进 disconnected | 先如实暴露；重连策略等真见到频率再定 |

## 6. 顺序

**R1 → R2 → R5 → R3/R4 → R6/R7。**

先把「能在远端跑一条命令并拿到退出码」打通（R1+R2），
它一通，G4 的一半就成立了；R5 让 Run 记录有环境；R3/R4 让它能被配置出来；
R6/R7 是体验。

**在 R1 之前先补的那件事已做完**（2026-08-11）。

**顺带纠正一处我自己写错的判断**：我一度断言「内核执行不进账本」，
核代码时发现不是——内核会话与 native 一样走 `beginTurn`，每段代码都有 Run。
**真实的缺口更具体，也更难看**：`idle` 分支无条件写 `completed / hasError: false`，
于是**跑挂了的代码在账本上是「完成、无错」**——那不是漏记，
是记了一件没发生的事，而账本本该是事实层（不变式 5）。已修，含变异验证与真链路 e2e。
