## 1. 判断

值得吸收的是目录传输的任务分解、有上限的并发、逐文件失败结果、空闲超时、通过临时文件提交上传，以及传输生命周期和面板显示分离的思路。

DAWN 已有良好的单文件流式传输、取消、临时文件、同名保护、进度和上传记录；远端会话还将工具、工作目录与内核接到了服务器。没有必要把 DSH 的 Cordis 服务、Web 路由或资源管理界面整体搬入 DAWN。

优先补齐“整个目录传得全、每个文件查得到、旧数据保得住”。不依据文档宣称插件已经解决大文件断点续传或已实测更快。

## 2. 源码对照

以下 DAWN 路径相对本仓库；DSH 路径相对上述参考目录。

### DAWN 当前需要先补的可靠性缺口

以下是静态控制流发现，未通过真机故障注入复现：

1. **批量上传没有等待文件完成，界面只跟踪最后一项。** `传一个` 在 `startUpload` 返回 `started` 后立即 resolve（`src/ui/App.tsx:3516`），而后端通过 `void e.upload(...)` 在后台继续执行（`src/workbench/backend.ts:4599`）。因此 `for ... await 传一个` 不构成按完成顺序执行的串行队列；也没有统一并发上限。
2. **覆盖可能先损失旧文件。** `RemoteExecutor.upload` 在 rename 前 unlink 原目标；若 rename 失败，catch 会删除 part，此时旧文件也已删除。现有正常覆盖测试没有覆盖这个失败窗口。
3. **远端探测错误被当成不存在。** `src/workbench/backend.ts:4567` 起对 `stat` 的所有异常都转成 false；权限不足和断线应和 ENOENT 分开。目录批次不能以未知状态作为覆盖或继续写入的依据。
4. **中断后清理结果不透明。** `src/remote/ssh.ts:493` 清理异常被忽略，断线时也不能保证远端 part 已清掉。应说明残留路径和清理状态，不宣称任何失败情况下都不会留下 part。
5. **任务记录生命周期过短。** `src/workbench/backend.ts:875` 在结束 60 秒后删除记录；批次失败清单和重试不能依赖这份短时 Map。

### 参考插件也有边界，不能照搬

- `src/client/SshFiles.jsx:167` 仍整文件 `arrayBuffer()` 后走 Base64 RPC；下载入口 `:122` 调有上限的读文件接口（默认 4 MiB，`src/index.js:136`）。虽然服务端另有流式 HTTP 路由，但这个界面入口没有使用它。DAWN 应继续让主进程读取本地路径。
- `src/sftp-dir.js:63` 和 `:68` 同时启动大小文件通道；实际是“大文件彼此不并发”，并非“大文件独占全部传输”。不能由注释推出独占带宽或加速结论；512 KiB 也不能当成实测最优阈值。
- `sftpUploadDir` 的目录集合来自文件的祖先路径，空子目录不会进入集合；DAWN 必须独立枚举目录。
- `sftpDownloadFile`（`src/index.js:4573`）直接写最终本地路径；其清理主要处理取消／超时路径，不是所有普通 I/O 错误。DAWN 的下载 part 后提交应保留。
- 目录枚举没有完整覆盖扫描阶段的取消与资源预算；DAWN 应限制深度、条目与同时打开的流，对扫描失败明示不完整。
- 保留 partial 不等于断点续传。本次研究的目录／单文件传输入口未发现完整的偏移续传、源文件身份验证与任务恢复闭环。
- 自动重连与命令透明重试不适用于本轮。DAWN 明确要求断线可见、人工重连；写入结果不明时不得自动重放。

## 3. 三条路线

| 路线 | 交付 | 取舍 |
|---|---|---|
| A：仅补现有多文件上传 | 将现有多个本地文件纳入队列，显示全部进度 | 改动较少，但不能完成用户选择的文件夹上传／下载 |
| **B：目录批次闭环，推荐** | 目录上下行、批次与逐文件进度、失败清单、失败项重试、基础可靠性 | 覆盖已明确的核心需求，复用现有连接、文件面板、下载位置及记账 |
| C：同时建设断点续传与跨重启恢复 | 在 B 上增加持久任务、偏移续传、源身份校验、恢复确认 | 大文件受益，但会显著扩大设计和验证范围；应在 B 验收后单独设计 |

## 4. 推荐范围的候选设计（待确认）

### 4.1 使用过程

1. 远端文件面板提供“上传文件夹”；用户通过系统目录选择器选择一个目录，传到当前远端目录下的同名文件夹。选定远端目录的操作菜单提供“下载文件夹”，落到已配置下载目录下的同名文件夹；根目录冲突默认另存一份。
2. 开始前显示服务器、源目录、目标目录；后台扫描目录，扫描阶段也能取消，尚未知道总量时不显示伪造的百分比。
3. 面板中展示批次摘要：目录、文件总数、已完成／失败／冲突／跳过数、已确认传输字节和目标路径。展开后看每个文件的相对路径、大小、进度、状态与错误。长清单分页读取，不把整个目录一次性塞入 React。
4. 关闭面板、切换聊天或切换服务器不取消传输；列表中的每条任务始终标明自己的服务器和目标，不能随当前选择换身份。
5. “取消批次”停止新任务并取消在传的文件，保留已完成文件；清理当前不完整文件，清理失败时列出残留路径。失败不会伪装成用户取消。
6. “重试失败项”重新检查源和目标，仅重传失败文件。它是从头重传该文件，不叫断点续传；源改变或目标出现新文件时回到待处理状态。

### 4.2 数据和覆盖策略

- 上传保留整个源目录的相对层级，包括空目录；只接纳普通文件和目录。符号链接、设备、socket 等不跟随，明确列为跳过及原因。
- 不做同步删除，不根据本地缺失删除远端文件，也不根据远端缺失删除本地文件。
- 对已有文件默认保留并标记冲突，不能凭同大小或同时间推断内容相同。用户逐项选“覆盖／另存一份／跳过”；不提供默认全覆盖。
- 对目录同名可以合并目录结构；目录和文件类型冲突停止该项，不替换目录树。根路径和相对路径都要检查，拒绝 `..`、异常目录条目和越界链接。SFTP 路径不能直接交给 shell tar，避免 chroot 命名空间不同。
- 上下行均先写目标同目录的唯一 part，成功并校验预期字节数后再提交；提交前检查取消与源是否发生可检测变化。大小检查能发现截短，不称为内容哈希校验。
- 显式覆盖远端文件时优先使用 `ext_openssh_rename`。扩展不支持则报告无法安全覆盖，保留旧文件，用户可选择另存；不退回先 unlink。

### 4.3 模块与状态

- `src/remote/ssh.ts`：SFTP 原语和单文件可取消传输、受控提交。补目录创建、lstat／realpath 等枚举与路径校验原语，不塞批次和 UI 状态。
- 新独立目录枚举与传输服务：扫描、清单、调度、取消、失败项重试、目标预留。位于主进程／后端；唯一拥有运行状态，避免把队列写进大 `App.tsx`。
- 初始采用每台服务器最多 3 个小文件、1 个大文件且总数最多 3 个的有界队列，大文件分界先固定 8 MiB；这些是保守起点，不是性能结论。验收记录吞吐和并发，遇到实际瓶颈再调整。
- 批次状态区分 scanning、running、completed、partial、failed、cancelled、interrupted；文件状态区分 queued、running、completed、failed、conflict、skipped、cancelled、interrupted。待冲突或有扫描缺口时不得显示“全部成功”。
- 持久化只存描述和结果，不存凭证、流、AbortController 或可执行闭包；重启后未终结项变为 interrupted，不自动开始。这样可以保留失败清单，但不声称跨重启续传。只通过明确动作重试，且重新验证目标和源。
- 协议提供开始批次、列出摘要、分页明细、取消和重试等能力；与旧单文件操作保持兼容。在同次实现里补 `scripts/mock-inference-server.mjs`。
- React 使用专门的批次视图／状态模块；文件字节不进入模型上下文和 IPC，沿用主进程文件流。上传结果继续写入既有上传记录；失败和清理结果分开记录。

### 4.4 分步实施与验收

| 切片 | 交付 | 必须验证 |
|---|---|---|
| 1：单文件可靠性 | 安全提交、保活、无进展超时、元数据错误分类、清理结果 | rename 失败旧文件保留；取消提交窗口；断线清理有界；正常单文件上下行兼容 |
| 2：目录服务与协议 | 枚举、空目录、有界并发、批次结果、持久化与分页、取消／重试 | 嵌套及空目录、零字节和 Unicode 文件、链接跳过、冲突、权限失败、短读、源改变、扫描取消、并发上限、重启中断和只重试失败项 |
| 3：文件面板真实流程 | 文件夹选择、目录下载菜单、批次和文件清单 | 真实 Electron 从目录选择走到磁盘文件验证；切换聊天／服务器状态不串；取消、失败清单、重试可实际操作；亮暗／窄窗口核对 |

执行时先建立有判别力的失败测试，再修改行为。新增协议必须同次补 mock。真实服务器的性能、兼容性和大数据量传输另留验收记录；假 SSH 与本地 Electron 不替代这些证据。

本轮不扩展数据库管理、ProxyJump、服务器表单重设计、自动连接、自动命令重放或断点续传。
