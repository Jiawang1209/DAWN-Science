# 默认自动安排复审（2026-11-08）

## 范围

用户纠正上一轮手工数字表单，要求默认由具体任务决定拆分与分工，数量作为可调整方案的结果。沿用原专项 worktree 的未提交成果，不另建执行器或推理通道。main d0b6ca78 保持不变。

按仓库长期路线单线实施；本记录为当前会话逐项复审，不称为独立子 agent 审查。本轮无提交/合并、推送、发布、正式 App 替换或付费 API 调用。

## 实际检查及修复

| 检查 | 结果与证据 |
|---|---|
| 任务粒度来自哪里 | 模型通过 propose_plan 的 arrangement 参数提交；UI 不以关键词或固定数量猜拆分。条件分支只在 mock fixture 中，生产代码不导入它。 |
| 显式自动请求遗漏结构 | 新增 requireArrangement，从原会话分支读取本次明确请求；省略时返回可纠正工具错误，不终止为成功方案。review-missing-structure-red.log 与后续通过日志。 |
| 正文与任务数一致 | 只在原 Markdown 中保存一份规范节，显示和批准都重新解析；模型 3→2、人工编辑 2→1、Native 批准 3→2 及同一方案簿/指纹存档有测试。 |
| 图与审阅约束 | 重复 ID、未知/重复依赖、环、并行共写/前后依赖、同角色审阅、审阅标记不一致均拒绝；批准前保留原 independentReview 要求。 |
| Markdown 旧功能 | 代码围栏内的安排示例不作为真实方案；合法旧式方案没有伪任务数量。review-fences-red.log 与通过日志。 |
| 用户可改输入的错误分类 | 返回 invalid_request，并使用既有双语 fault 文案；未扩大 fault原样 白名单。全量首次发现 fault-i18n 准入失败，原日志保留。 |
| 不误发会话 | 读取能力、租约和只读设置之后均验证 owner/窗口代次/取消信号；无效会话、不支持能力、活跃父子执行不自动降级或排队；草稿保留。 |
| 规划失败与取消 | 取消信号阻止迟到发送；中止只针对仍处规划期的原 owner。回合结束但没有新有效安排会显示原因入口；新有效方案到达会清除相应等待错误。 |
| 采纳与恢复 | 原 answerPlan、方案簿版本/状态、批准文件和指纹、原执行发送仍是唯一链路；没有新增 DB/IPC，没有将规划角色当冻结执行者或验收证明。 |
| 原成员入口 | 保留上一轮查看、续问、纠偏、停止、Bot 只读、展开返回和会话隔离；相关用例继续复验。 |
| 取消证据的有效性 | 首次用 reasoning 延迟模拟规划等待，但工具回复不走该分支，导致点击前方案已经完成。保留失败 trace，改用既有 firstChunkDelayMs 旋钮；不修改产品取消逻辑或测试超时。最终在途取消单独复验。 |
| 首字前取消 | 首包延迟后真实复现：原对话停止会清本地等待，新入口只调宿主，取消后仍转圈。已按原转录槽补 inputId 绑定的界面确认；只在宿主成功返回且 owner/代次/输入仍匹配时应用，下一次输入重新等待，两槽互不串。cancel-waiting-red.log、stop-generation-red.log 及后续绿灯/真实桌面取消后再规划验证。 |
| 迟到停止不伤新轮 | stopAutoArrangement 在读取原方案模式之后、调用 abort 之前核对输入身份；宿主返回后再核对一次。旧读取不能停新输入，迟到确认不能清新输入；不将停止确认写成持久已排空事实。 |
