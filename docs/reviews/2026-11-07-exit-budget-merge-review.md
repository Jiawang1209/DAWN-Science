## 发现并修复

1. **P1 启动中的会话漏收。** `stopAll()` 仅遍历已绑定会话，遗漏仍在新建或恢复的会话；后者可能在收尾返回后完成绑定。复用原启动 Promise 表跟踪新建与恢复，批量停止取启动/已绑定身份并集，退出判断同时认识启动预备期。两个管理器门闩与真实 Workbench 装配测试先红后绿。退出期间启动可以被取消或失败，不能把“创建请求一定成功”当成验收条件，重点是没有迟到的活绑定。
2. **P2 下层清理失败被吞为 drained。** 会话、内核和 MCP 原本均有尽力清理路径。保留普通调用兼容，只为退出启用 `reportErrors`；所有清理都尝试并等待后才汇总错误。内核共享原始结果，先来的普通调用不能吞掉后来的退出诊断。MCP 原池跟踪原始 close Promise，包含已从连接表摘除的关闭和替换；退出等待这些 Promise，也能看见 SDK 原关闭错误。真实 stdio 服务器、并发门闩及失败注入先红后绿；MCP 有连接、启动或在途关闭时触发原有界收尾。
3. **P2 桌面退出验收只看 code=0。** 新增检查原生收尾 deadline、失败和外层兜底；退出码为零也不得据此通过。原生诊断缺失、损坏或异步收尾缺少结果分别标记未知/不完整；共享诊断目录仅检查最近一次同 PID 实例。产品仍正常尝试退出，诊断缺席使测试报告未核验，不改变产品控制流程。
4. **P2 资源快照读取失败时整条退出事实丢失。** 将资源观察与事件落盘分开，API 异常时仍保存生命周期，并明确 `resourceSnapshotAvailable=false`；没有把未知资源计数当作完整快照。

原取消、epoch、锁持有到排空、预算结算及恢复不重放语义保持；1500ms 内层等待、4000ms 外层兜底和原 MCP 5000ms 关闭上限没有提高。诊断不记录模型正文、请求、URL、配置或密钥。代码自审覆盖新启动表生命周期、并发关闭、错误聚合、回调失败和定时器清理，不冒称独立代理审查。
