## 二、签名到底买到了什么（事实，不是推断）

**丢 key 只发生在 mac 上，根因是钥匙串 ACL 认的是「指定要求」（designated requirement）。**

- ad-hoc 签名的 `.app`，指定要求就是**这一份二进制的 cdhash**——每打一次包都变，于是新版读不了旧版建的
  「dawn-science Safe Storage」（2026-08-28 作者机器上抓到，`credentials.json` 六条全解不开）。
- Developer ID 签名的 `.app`，指定要求是 `identifier "science.dawn.app" and anchor apple generic and … leaf[subject.OU] = <TEAMID>`——
  **只要 bundle id 与 Team ID 不变，每一版都满足它**。这就是 Claude / Codex 桌面版更新不丢东西的原因。
- Windows 的 `safeStorage` 走 DPAPI（按用户，不按二进制）、Linux 走 libsecret/kwallet（按会话）——**按 Chromium `os_crypt` 的实现，
  两者都不会因换二进制而读不出**。这条是读实现得出的，**不在真机验过**，写进 `docs/打包与发布.md` 时照实标注。

所以签名在 mac 上一次性买到四件事（09-06 规格原话）：替换、quarantine、Gatekeeper、钥匙串。**本规格只做前三件的「让它不再是问题」
与第四件的「迁移那一跳」；应用内更新的换包逻辑不重写。**

## 三、定案

### S1 · 两份配置：基础版照旧 ad-hoc，发布版 `extends` 它

```
electron-builder.yml           ← 不动它的签名语义：identity "-"（本机 pack、test:packaged、rehearse-*、没证书的贡献者都靠它）
electron-builder.release.yml   ← extends: electron-builder.yml
                                  mac.identity: "<名字> (<TEAMID>)"   ← D10
                                  mac.forceCodeSigning: true          ← 找不到证书就红，不许悄悄出一个没签的包
                                  mac.notarize: true
                                  mac.hardenedRuntime: true            ← 与基础版相同，写一遍让判据不依赖合并语义
```

**为什么不是一份**：一份写死 Developer ID，没证书的机器上 `npm run pack` 直接红——`test:packaged`、四个 `rehearse-*` 都坐在它上面；
一份写 `"-"` 再靠 CI 命令行 `-c.mac.identity=…` 覆盖，判据就判不到「发出去的那份」（覆盖在 YAML 之外）。
`extends` 在 electron-builder 26.15.3 是 `deepAssign`（`app-builder-lib/out/util/config/config.js:173`），`mac:` 按键合并而不是整块覆盖；
计划 Task 2 用 `release/builder-effective-config.yaml` 实际核一次，不靠读源码。

**为什么要 `forceCodeSigning`**（读源码查实的，2026-09-27）：`identity` 写了名字但钥匙串里找不到时，`MacTargetHelper.findSigningIdentity`
走 `reportError(…, forceCodeSigning)`——**不强制时只打一行 warn 然后跳过签名**，产出的正是 0.0.6 那种「已损坏」的碎签名包。
`forceCodeSigning` 在 `PlatformSpecificBuildOptions` 上，可以只加在 `mac:` 下，不会连累 Windows（D2 推迟时 Windows 仍不签）。

**`notarize` 也有同样的静默**：`notarizeIfProvided` 在环境变量一组都凑不齐时 `log.warn("skipped macOS notarization")` 然后继续。
YAML 里没有「强制公证」的开关——所以挡它的是**构建前的环境自检**（S5 `check-signing-env`）与**构建后的验签**（S4，`spctl` 必须说 `Notarized Developer ID`）。

### S2 · Hardened runtime 与 entitlements：按这个应用实际做的事逐条过

`hardenedRuntime: true` 早就开着（ad-hoc 时也开），公证要求它。entitlements（`packaging/entitlements.mac.plist`，主进程与子进程共用）：

| entitlement | 这个应用为什么要 / 不要 | 定案 |
|---|---|---|
| `cs.allow-jit` | V8 JIT：主进程、渲染进程，以及 `ELECTRON_RUN_AS_NODE=1` 起的子进程（`src/runtime/acp/launch.ts` 起 ACP 适配器、`subagent-child.js`、`dawn-mcp-server.mjs`——它们是**同一个 Electron 二进制**，吃 `entitlementsInherit`） | 留 |
| `cs.allow-unsigned-executable-memory` | 较老 Electron / 某些原生模块需要；Electron 43 上可能已不需要 | 这一轮留（D4），Task 1 量一次删掉会不会坏 |
| `cs.disable-library-validation` | ad-hoc 时**必需**（基础版判据守着）。Developer ID 下，electron-builder 会用同一张证书签包里每个 Mach-O（`better-sqlite3`、`node-pty` 的 `pty.node` 与 `spawn-helper`、`zeromq`、`pi-tui` 的 `darwin-platform.node`），同 Team ID 的库校验本来就过 | 这一轮留（D4），同上量一次 |
| `cs.allow-dyld-environment-variables` | 全仓零处 `DYLD_`；它还让「同用户的任意进程往我们进程里注库、借我们的钥匙串身份」多一条路 | **删**（D4） |
| `automation.apple-events` | 全仓无 `osascript` / AppleScript（2026-09-27 grep） | 不加 |
| `device.camera` / `device.audio-input` / 屏幕录制 | 无 `getUserMedia`；取色器**特意不走** `desktopCapturer`（`src/ui/eyedropper.tsx` 头注释） | 不加 |

**不受 hardened runtime 管的**：Python / R 内核、`ssh`、用户的 shell、Playwright 起的 Chrome——它们是**别的二进制、别的进程**，
各自带自己的签名，hardened runtime 不限制我们 `spawn` 它们。远端内核更与本机签名无关。

**包内不许有东西在运行时写自己**：签名封住了 `Contents/` 下每个文件。`asar: false` 意味着 `Resources/app/` 是普通目录，
任何往里写的动作（例如某个技能目录里的 `.py` 被 import 时生成 `__pycache__`）都会让 `codesign --verify` 失败。
技能管理已经拒绝改「自带目录」里的 SKILL.md（`backend.ts` 7.17 守卫），但**没人验过运行一圈之后包还完整**——
S4 的验签在 `test:packaged` **之后**再跑一遍，就是为这一条。

### S3 · 公证 + staple：交给 electron-builder，但判据是自己的

- electron-builder 在 `sign()` 末尾调 `@electron/notarize`（本仓 2.5.0），`notarize()` 提交 `notarytool` 并**默认 staple `.app`**；
  之后才从这个已 staple 的 `.app` 打 `dmg` 和 `zip`。所以 zip 里（应用内更新下的那份）与 dmg 里的 `.app` 都自带公证票据，离线首启也过。
- 环境变量（electron-builder 认的名字，别改）：D1 默认 `APPLE_API_KEY`（**`.p8` 文件的路径**）+ `APPLE_API_KEY_ID` + `APPLE_API_ISSUER`；
  本机用 `APPLE_KEYCHAIN_PROFILE=dawn-notary`。
- 两个架构两次公证（arm64、x64 各一个 `.app`），每次 2–15 分钟不等；CI 的 mac job 超时放到 60 分钟。
- 公证被拒时，`notarytool` 的 submission id 会在日志里——`xcrun notarytool log <id> --keychain-profile dawn-notary` 读具体哪个文件
  （常见：某个预编译 Mach-O 用了 10.9 以前的 SDK、没带 secure timestamp）。**第一次公证的日志不论成败都读一遍**（Task 1）。
- （D8 若量出来要补）dmg 公证：`xcrun notarytool submit <dmg> --wait` → `xcrun stapler staple <dmg>`，放在 electron-builder 之后、验签之前，
  写成 `scripts/notarize-dmg.mjs`；**默认不做**。

### S4 · 验签：一个脚本，本机与 CI 同一份

`scripts/verify-mac-signature.mjs <.app 或 .dmg 路径…>`，任一条不过就非零退出并**把原话印出来**：

```bash
codesign --verify --deep --strict --verbose=2 "DAWN Science.app"    # 退出码 0，"valid on disk" + "satisfies its Designated Requirement"
codesign -dv --verbose=4 "DAWN Science.app"                          # TeamIdentifier=<APPLE_TEAM_ID>；flags 含 runtime；Authority=Developer ID Application: …；Timestamp= 存在
codesign -d --entitlements :- "DAWN Science.app"                     # 不含 allow-dyld-environment-variables；含 allow-jit
spctl -a -vv -t exec "DAWN Science.app"                              # "accepted" + "source=Notarized Developer ID"
xcrun stapler validate "DAWN Science.app"                            # "The validate action worked!"
# dmg（D8 默认不公证时只查前两项）：
codesign --verify --verbose=2 X.dmg ; spctl -a -vv -t open --context context:primary-signature X.dmg ; xcrun stapler validate X.dmg
```

**解析与判定写成纯函数**（`scripts/lib/mac-signature.mjs`），喂 `codesign` / `spctl` 的真实输出样本做单测——
这是准入规则 ② 的形状：判得出的规则配测试，而不是靠人每次肉眼看。

另外每个 `.app` 里**所有** Mach-O 都要是我们的 Team ID 签的：
`find "…app" -type f -perm +111 -o -name '*.node' -o -name '*.dylib'` 逐个 `codesign -dv`，Electron 自带框架也在其中
（electron-builder 会重签它们）。这一条挡的是「某个新加的原生依赖没被签到」。

### S5 · CI：只在打 tag 时签；secrets 缺了当场红

`release.yml` 的 mac 那一格：

1. **环境自检**（`scripts/check-signing-env.mjs --mac`）：列出**缺的变量名**（只打名字，**永不打值**），缺一个就红。
   这一步放在 `npm ci` 之后、`npm run build` 之前——等 20 分钟构建完才发现没配 secret 是最贵的失败。
2. 把 `APPLE_API_KEY_P8` 写成 `$RUNNER_TEMP/AuthKey.p8`（0600），`APPLE_API_KEY` 设成这个路径；job 末尾 `if: always()` 删掉它。
3. `npx electron-builder --mac --config electron-builder.release.yml --publish never`，env 里 `CSC_LINK: ${{ secrets.MAC_CSC_LINK }}`、
   `CSC_KEY_PASSWORD: ${{ secrets.MAC_CSC_KEY_PASSWORD }}`（electron-builder 自己建临时钥匙串导入、用完删）。
4. 对 `release/mac-arm64/*.app`、`release/mac/*.app`（x64）、两个 dmg 跑 S4 脚本。**验签红 = 这个平台没打出来**（D3），不上传产物。
5. `workflow_dispatch`（手动）与 PR：**不签**（secrets 不给 fork，且手动那条只是出 artifacts 看看）——mac 格走基础配置、出 ad-hoc 包，
   产物名照旧；只有 tag 触发才走发布配置。判据（计划 Task 6）扫描 workflow：tag 分支的 mac 命令必须带 `--config electron-builder.release.yml`、后面必须有验签步骤。

secrets 只在 `env:` 里按步骤给，**不在 job 级 env 铺开**——Linux / Windows 那几格拿不到 mac 的证书。

### S6 · 迁移：ad-hoc → Developer ID 那一跳（失败必须出声）

装着 0.0.x（ad-hoc）的人换到第一个签名版，有三条路，**哪条会丢 key 取决于一个还没量的事实**：

| 路 | 新版能不能拿到明文 | 预期 |
|---|---|---|
| **A 应用内更新**（点「下载并安装」） | 旧版还活着、能解开，按 U5 把明文写进 `handoff.json`；新版首启读它、用**自己的** `safeStorage` 重新加密 | **key 不丢**——前提是签名版的 `safeStorage` 在「钥匙串里已有一个 ad-hoc 建的同名项」时可用。未验（M1） |
| **B 手动下 dmg 覆盖安装** | 没人写 handoff；新版面对的是 ad-hoc 建的钥匙串项 | 系统可能弹「DAWN Science 想使用钥匙串中的机密信息」要登录密码（点「始终允许」则 key 不丢），也可能直接读不到（**丢最后一次**）。未验（M1） |
| **C 全新安装** | 没有旧东西 | 无事 |

**M1（计划 Task 1 与 Task 12 必须量出来的）**：签名版首次启动时，面对 ad-hoc 版建的「dawn-science Safe Storage」——
弹不弹框、`isEncryptionAvailable()` 回什么、旧密文解不解得开、A 路 handoff 能不能落回去。**Release 说明与首启提示的措辞照实测结果写**，
不按本表的「预期」写。下面两处是**按最坏情况（B 路丢）**准备的，量出来更好就删掉对应句子：

- **首启提示**（界面）：`listCredentials` 多一个可选字段 `signing`（协议 8.1，纯新增）。主进程读自己的签名身份
  （`codesign -dv` 解析 `Signature=adhoc` / `TeamIdentifier=`，mac 独有、不在启动路径上、与钥匙串预热同一时机），
  并与 `userData/signing.json` 里记的上一次比：
  - `broken` 非空 **且** 这一次是 Developer ID **且** 上一次是 ad-hoc 或没记录 → `signing.transition = "adhoc-to-developer-id"`，
    向导与设置里那句换成：**「这一版起 DAWN Science 有了正式签名。系统钥匙串认不出旧版存的 key（{服务名}），请最后重填一次——以后更新不会再丢。」**
  - `broken` 非空但已经是签名版对签名版 → 不再说「应用更新后钥匙串换了身份」（那句话在签名之后是错的），改说
    **「系统钥匙串没让这一版读出之前存的 key（{服务名}）——可能点过「拒绝」或钥匙串被重置过，请重新填写」**。
  - 仍是 ad-hoc（本机 pack、手动那条 CI）→ 保留今天的原句。
  - 读签名身份失败（`codesign` 不在、输出看不懂）→ `signing` 缺省，界面按今天的原句，**`startup.log` 记一行原因**，不猜。
- `startup.log` 在每次启动记一行 `签名身份：developer-id <TEAMID>` / `adhoc` / `读不到：<原因>`，迁移那一次另记 `签名迁移：ad-hoc → developer-id，N 条凭证解不开`。
- **Release 说明**（`packaging/release-notes.md`，release job 把它放在自动生成的说明前面）：写清「从 0.0.x 升上来：用应用内更新 key 保留 / 手动装可能要重填一次，
  这是最后一次」（措辞以 M1 为准）；「以后不需要右键打开」；以及「0.0.6 及以前报『已损坏』的那条 `xattr -cr` 不再需要」。

### S7 · 签名之后的应用内更新

- **换包前验签（D7）**：`src/update/换包.ts` 在「核对版本」之后、「备份旧的」之前加一步：新 `.app` 必须 `codesign --verify --deep --strict` 通过；
  正在跑的这一版有 Team ID 时，新包的 Team ID 必须相同。任一不过：**不换**，状态进 `failed`，原话写 `新包签名不对（…），没敢换`——
  与「版本对不上，没敢换」同一个口吻。验签作为 `换包依赖` 的一个注入函数，测试里是替身。
- **U5 交接保留（D6）**：签名版之间它是空操作（新版自己解得开 → 删 handoff）。`rehearse:handoff` 与 `rehearse:update` 照旧留着。
- `换包.ts` / `交接.ts` / `本机安装器.ts` 文件头里「我们这一轮不签名」的说法改成现状（签名之后 quarantine 与 Gatekeeper 也不再是地基，但**换包仍不经过 LaunchServices 以外的东西**）。

### S8 · Windows 的路（D2 默认不走）

签了买到的只有：SmartScreen 不再拦「未知发布者」（EV 立即、OV / Trusted Signing 需要攒下载信誉）、安装器与 `DAWN Science.exe` 显示发布者名。

- **Azure Trusted Signing**（推荐的那条，如果要走）：`win.azureSignOptions: { publisherName, endpoint, certificateProfileName, codeSigningAccountName }`
  写进 `electron-builder.release.yml`；CI 给 `AZURE_TENANT_ID` / `AZURE_CLIENT_ID` / `AZURE_CLIENT_SECRET`。
  同时把 `win.signAndEditExecutable` 改回 `true`（现在是 `false`：不签时它还会跳过 rcedit）。
- **OV 证书 + 云 HSM**：`win.signtoolOptions.sign` 指向一个自定义脚本调厂商 CLI（例如 SSL.com CodeSignTool）；厂商相关，定了再写。
- 验证：`signtool verify /pa /v "DAWN-Science-…-win-x64.exe"` 与 PowerShell `Get-AuthenticodeSignature`，`Status` 必须 `Valid`。
- **本机验不了**（作者只有 mac）：与 08-21 那批 Windows 老账放在一起，标「未在真机验过」。

## 六、风险

1. **M1 没量之前，迁移那句话说不准**——所以 S6 的文案按最坏写、量完再收。不许先写「key 会保留」。
2. **公证第一次多半不过**：包里 800+ MB、若干第三方预编译 Mach-O（`zeromq` 带 `libc-72` 与 `libc-115` 两套 x64 构建）。读 `notarytool log`，
   按文件定点处理（重签 / `signIgnore` 掉用不到的那一份 / 排除出 `files`），**别为了过公证去关 hardened runtime**。
3. **包内被写**（S2 末）：验签放在 `test:packaged` 之后跑，红了先找是谁写了包，不许用「验签只在打包后跑一次」绕过去。
4. **证书到期**：Developer ID Application 证书 5 年；到期前签的包因为有 secure timestamp 仍然有效，但**换证书（新私钥）不换 Team ID 时指定要求不变**，
   钥匙串照认。会员费断缴则无法再公证——那时 D3 让 mac job 红，不会悄悄发 ad-hoc。
5. **CI 上 `CSC_LINK` 导入失败的报错很含糊**（`security: SecKeychainItemImport` …）：自检脚本只查「在不在、base64 解不解得开、解出来是不是几 KB」，
   不自己去开 p12（runner 上的 LibreSSL 对新式 p12 加密支持不一，自己验反而误报）；electron-builder 导入失败时，那一格的日志里由自检预先印一行
   「若下面报 SecKeychainItemImport，是 MAC_CSC_LINK 或 MAC_CSC_KEY_PASSWORD 不对」。
6. **在作者自己的 macOS 账户里起签名版，会碰他真在用的那把钥匙串项**：钥匙串项按名字（「dawn-science Safe Storage」）落在登录钥匙串里，
   与 `--user-data-dir` 无关；应用在首帧之后就会预热钥匙串。签名版对 ad-hoc 建的那一项做什么（M1）还不知道——万一是「读不到就新建覆盖」，
   作者手上正在用的 0.0.11 就丢 key。所以**凡是启动签名版的步骤，一律在专门的测试 macOS 用户里做**；
   `codesign` / `spctl` / `stapler` / `notarytool` 不启动应用，可以在作者账户里跑。
7. **两个架构共用一次 `electron-builder --mac` 调用**，任一公证失败整格红——与 D3 一致，接受。
