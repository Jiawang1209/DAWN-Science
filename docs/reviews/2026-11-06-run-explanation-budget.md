## 做了什么

### A：知道为什么等待与如何结束

原 OrchestrationStore 增加可选事件、阶段和结算耗时；仍由原状态机决定准入和恢复。历史最多保留最近 256 条，单调序号保留，明确显示较早历史省略；旧记录没有的历史不倒推。内容只有宿主身份、时间、阶段、锁范围/占用者和验收状态，不复制提示词、模型正文或工具原文。

AsyncLocalStorage 携带原 ownerSessionId/childId/epoch，贯穿普通 Pi 子进程、Team 和 Bot 适配器。原 BotOutputLocks 继续维护实际锁，新增观察只说明活动持有者及公平队列的前序等待者，不改变 inode、别名、读验证锁或排空规则。观察写入出错会显示缺失，不让它跳过资源清理。

现有“团队”面板的运行总览显示：锁等待、冻结输入核验、后端执行、宿主验收；各阶段的已结算耗时；关键历史。执行完成与宿主验收仍分开。磁盘快照中的阶段/占用关系只称为历史，当前进程与占用仍未知。复用失效原因继续来自原流水线/批量投影，没有另造一份规则。

实际效果：`phase-a-lock-wait.png`、`phase-a-history.png`。真实两个 Pi 子任务使用同一工作区锁，等待行显示持有者；最终两任务结算且历史保留等待。跨父会话同产物及取消后不提前释放另由真实锁池集成测试覆盖。

### B：限制累计委派，重启不归零

预算范围是当前父会话的统一编排：普通子任务、Team、Bot、续问及返修；根会话模型请求、独立内核和其他父会话不计入。界面称“会话委派预算”，不能把它当成完整账户费用封顶。

- 执行轮次：计实际进入统一编排的轮次，包括在锁/核验阶段停止的轮次；准入前检查，最后合法轮次可完成。
- 总历时：从首轮准入起计算，包含暂停和离线；截止后走既有取消，等实际后端清理完才释放执行槽。
- token：累计已结算 input + output + cacheRead 的安全整数字段；缺失、partial、异常或恢复时尚未结算的用量明确为未知，不当作零。token 限额按结算边界检查；未知用量阻止该限额下的新轮次，在途并发可能产生超额。

预算与 epoch 准入、结果结算在同一 state.json 原子提交。在途身份只结算一次；重建时未结算轮次增加未知次数，不自动重跑。旧代次计入可知轮次；无代次但有返回结果时至少计入一轮未知用量，不用 updatedAt 编造首次开始时间。原契约、权限和版本绑定不变。

只有 UI 的版本化 `setRunBudget` 操作能改限额；模型无修改预算工具。expectedRevision 防止旧界面覆盖新消耗，冲突后可显式重新读取；调整或清空限额都保留已用记录，不自动恢复旧消息。离线或其他运行时只读，不建立竞争写入的 Store。协议 minor 为 8.46，产品包版本仍 0.0.44。

实际效果：`phase-b-limit.png`、`phase-b-recovery.png`。两轮上限下第三个 Pi 子进程未启动；重启后已用仍为两轮，旧结果一致。`phase-b-elapsed-drained.png` 和 `elapsed-process-drain.json` 验证实际 sleep 15 子进程被六秒总历时限制停止，新增进程树退出，账本 active 为空。

## 审查中复现并修正的边界

本轮是一条实现主线的代码自审，不冒称独立审查。

1. 普通外部取消和应用关闭也应留下 cancel-requested 历史；补齐同一取消门，但保持排空语义。
2. 冷读原先只校验子身份，新增历史和在途账本也需校验会话身份、顺序和代次；在线恢复与只读观察复用同一无副作用验证。
3. 分数或超安全整数的 provider 用量不能让原本成功的后端卡在未结算；保留可核验部分并标记未知，既不编造零，也不跳过终结。
4. 系统时间向后调整可能使第一次 timer 早于总历时截止；重新安排剩余时间检查。恢复期间进一步复现墙钟前跳但旧长 timer 仍在等待，改为有工作时至多每秒复核一次到期，不周期写盘；前跳/回拨均先红后绿。
5. 普通无契约 Team 不显示未真正发生的“宿主验收”阶段；契约判断和验收放行仍走旧实现。
6. UI 预算冲突可重新读取当前版本，不让旧草稿永久携带旧版本；异步旧会话响应不进入新会话。协议端将这个预期冲突作为 UserFacingError 返回，避免被归一成不可操作的内部错误；真实存储故障仍不暴露原始信息。
7. 旧格式已有返回结果、但 epoch 为零时，至少确认一轮未知用量，不能把旧结果视为零消耗。
