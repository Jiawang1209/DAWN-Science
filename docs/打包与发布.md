# 打包与发布：给一台新电脑一个独立的 DAWN Science

> 设计与理由见 `docs/superpowers/specs/2026-08-27-打包-design.md`。这里只写怎么做。

## 一句话

**在哪个系统上要安装包，就在那个系统上打**：

```bash
git clone <仓库> && cd dawn-science
npm ci                # 会按本机平台拉对应的原生预编译件（better-sqlite3 / node-pty / zeromq）
npm run dist          # 当前平台默认目标；产物在 release/
```

| 系统 | 命令 | 产物 |
|---|---|---|
| macOS | `npm run dist:mac` | `release/DAWN-Science-<版本>-mac-arm64.dmg`、`…-x64.dmg`、同名 `.zip` |
| Windows | `npm run dist:win`（或在 mac 上交叉打，见下） | `release/DAWN-Science-<版本>-win-x64.exe`（安装器）、`…-win-x64-portable.exe`（免安装） |
| Linux | `npm run dist:linux` | `release/DAWN-Science-<版本>-linux-x86_64.AppImage`、`…amd64.deb` |

打包机本身要有：Node 22、git；Linux 另要 `build-essential python3`（node-pty 现场编译）和 `libfuse2`（AppImage 打包工具用）。`.deb` 要求 `package.json` 里有 `homepage`——已填仓库地址。

**交叉打包（在 mac 上出别的平台的包）——实测口径（2026-08-27）：**

| 目标 | 能不能从 mac 打 | 原因 |
|---|---|---|
| Windows x64 | **能**：`npx electron-builder --win --x64 --publish never` | 三个原生模块的 win32-x64 预编译件都随 npm 包带着（better-sqlite3、node-pty 含 conpty、zeromq）。**但没在真 Windows 上验过**——第一次拿到 Windows 机器先跑 `test:packaged` |
| Linux | **不能直接交叉打**，但**可以在 Docker 里打**（2026-09-05 实测走通） | node-pty 的 npm 包不带 linux 预编译件，Linux 上 `npm ci` 时现场编译；从 mac 打出来的包终端会哑。见下面「在 Docker 里打 Linux 包」 |
| macOS 另一种芯片 | 能（`dist:mac` 本来就 arm64 + x64 各出一份） | 三个模块的 darwin-x64 / darwin-arm64 件都在 |

## Windows：能打包，未经验证（2026-08-28）

代码从没在 Windows 上跑过。首轮 CI 在 windows-2022 上 `npm test` 红了 25 个文件，是二十多个独立的兼容问题
（绝对路径判断、路径分隔符、文件权限 0600、命名管道、时区、CRLF、`bash`……），不是一轮能修完的。
当前处理：修了两个必撞的（`isAbsolute`、`data/raw` 分隔符），Windows runner **只构建不测试**，Release 说明里标「未经验证」。
移植是下一项工作，靠真机反馈驱动。

## 打不开时先看这里

应用在窗口出现之前就开始写 `startup.log`（2026-08-28 加的）：

| 平台 | 文件 |
|---|---|
| macOS | `~/Library/Application Support/dawn-science/startup.log` |
| Windows | `%APPDATA%\dawn-science\startup.log`（资源管理器地址栏直接粘） |
| Linux | `~/.config/dawn-science/startup.log` |

目录名取自 package.json 的 `name`（小写 `dawn-science`），不是产品名。

**在作者自己的电脑上测「全新安装」**：这个目录里有上一次打包版的数据（首启还会从开发版的 `Electron/` 迁一份），有 key 就不亮向导。要看全新的样子：退出应用，把 `dawn-science/` 和 `Electron/` 两个目录改名备份，再开；测完改回来。或者新建一个 macOS 用户账户——那才是别人机器上的样子。

三种读法：**文件不存在** → 主进程根本没起来（被杀毒/SmartScreen 静默拦了，或便携版还在往 `%TEMP%` 解压——它每次启动要先解 700 MB，慢机器上要等半分钟以上，先试安装器版）；**有「主进程模块已加载」没有「app ready」** → Electron 起来了但没到 ready；**有「未接住的异常」** → 那一行就是原因，会同时弹框。

## 在 Docker 里打 Linux 包（2026-09-05 走通，两个架构都验过）

macOS 上装着 Docker Desktop 就够。**两条纪律**，都是踩出来的：

1. **不要在挂载的宿主目录里构建。** Docker Desktop 的共享目录在模拟架构（mac 上跑 amd64）下复制不可靠——
   踩到过一个零字节且权限成 `--w-------` 的残留文件（`npm run build` 报 EACCES），
   以及 `dist/skills` 只复制到一半（少了 `SKILL.md`，electron-builder 报 ENOENT）。
   **把源码 `git archive` 通过 stdin 喂进去，全程在容器自己的文件系统里构建，只把成品拷出来。**
2. **x64 与 arm64 各打各的**：node-pty 只编得出本机那一种架构。x64 用 `--platform linux/amd64`（Apple 芯片上是模拟，慢），arm64 用原生。

```bash
# 容器里要装：build-essential python3（编 node-pty）、fakeroot（打 .deb）、file、desktop-file-utils
# 想在容器里起起来验，再加：xvfb 与 GTK 那组
#   libgtk-3-0 libnotify4 libnss3 libxss1 libasound2 libxtst6 xauth libgbm1
#   libatk-bridge2.0-0 libatspi2.0-0 libcups2 libxcomposite1 libxdamage1 libxfixes3 libxrandr2 libxkbcommon0
git archive HEAD | docker run -i --rm --platform linux/amd64 -v "$PWD/out:/out" node:22-bookworm bash -c '
  <装上面那些>
  mkdir /work && cd /work && tar xf -
  npm ci && npm run build
  npx electron-builder --linux --x64 --publish never
  cp release/*.AppImage release/*.deb /out/'
```

**在容器里验一次**（`xvfb-run -a node scripts/test-packaged.mjs`）——这是 Linux 包唯一被真正起过的方式。
两条会把人带偏的报错：缺 GTK 时 Electron 说的是 `libgtk-3.so.0: cannot open shared object file`，
而 Playwright 那层把它包成一句没头没脑的 `Process failed to launch!`（**不是沙箱问题**）；
以 root 直接起要 `--no-sandbox`，但 `_electron.launch` 自己会带上，走自测那条路不用管。

## 打完必须验一次

```bash
npm run pack            # 只出解包目录 release/<平台>-unpacked/，不出安装器
npm run test:packaged   # 起那个产物，四个原生模块各碰一次：开库、发一句、开终端、列内核
npm run rehearse:fresh  # 全新电脑演练：不带任何 DAWN_* 变量、临时 HOME、干净 userData、.env 里的真 key，走完首启→对话→Python→终端
npm run rehearse:update # 更新演练：userData 里预放一份上一版钥匙加密的 credentials.json，验「窗口不卡、说清要重填、重填能聊」
```

`rehearse:update` 是 2026-08-29 加的：`rehearse:fresh` 没有旧数据，抓不到「更新过的用户」那条路——而未签名包每次更新都走这条路。
它同时盯着 startup.log：「无法解密」必须出现在「钥匙串预热」之后，否则就是又有人把钥匙串放回了启动路径。**三个都要绿。**

`rehearse:fresh` 是 2026-08-28 打包版发出去被人抱怨之后加的：`test:packaged` 全绿的那一版，在全新机器上窗口空白 5–60 秒、
一开口走 claude CLI、向导根本不亮——它验的是原生模块，不是「一个没装过的人会看到什么」。**两个都要绿。**


`test:packaged` 绿了才算这个平台的包能用。**它只验当前平台。**

## 没签名的包，每次更新都会让上一版存的 key 解不开（2026-08-28 作者机器上抓的）

macOS 钥匙串里那把「dawn-science Key」认的是**建它的那个二进制**。未签名的包每打一次都是一个新二进制，
新包读不出上一版加密的 `credentials.json`——deepseek、kimi、SSH 口令全部「无法解密」。
应用现在会诚实：这些 key 从「已配置」里拿掉、列为「需要重新填写」，向导会亮并说明原因，`startup.log` 里有记录。
**用户要做的只是重新填一次。** 这件事签名之后就没有了——是那 99 美元真正买到的东西之一。

## 装到新电脑上

| 平台 | 安装 | 第一次打开（因为没签名） |
|---|---|---|
| macOS | 打开 dmg，把 DAWN Science 拖进 Applications | 右键 App → 打开；仍打不开就 `xattr -cr "/Applications/DAWN Science.app"`。macOS 15 起要去「系统设置 → 隐私与安全性」底部点「仍要打开」 |
| Windows | 运行 `…-win-x64.exe` 按向导装；或直接跑 `portable.exe` | SmartScreen：「更多信息 → 仍要运行」 |
| Linux | `chmod +x *.AppImage && ./DAWN-Science-*.AppImage`；或 `sudo dpkg -i *.deb` | AppImage 需要 FUSE2：`sudo apt install libfuse2` |

**第一次打开**：没有任何 API key 时首屏是向导——选服务商、填 key、保存，「开始使用」就亮了。同一屏可以顺手「检测本机解释器」，从这台电脑上已有的 Python / R 里选一个（可选，不配也能聊；缺 ipykernel / IRkernel 会给一句装法，装由你自己在终端里做）。「先跳过」之后底部红字仍在，点它回到向导。

**软件本身不需要 Node.js。** 但下面这些是它调用的外部东西，要用哪样就装哪样，软件里每一处缺失都会明说：

| 要做什么 | 要装 | 缺了会看到 |
|---|---|---|
| 笔记本 / `run_code`（Python） | Python 3 + `pip install ipykernel`，然后在「设置 → 内核」填解释器路径 | 「还没配 Python 的解释器路径」 |
| R 内核 | R + `IRkernel` | 「还没配 R 的解释器路径」 |
| 项目的 git 事实（变更、分支） | git | 概览格里没有变更 |
| ACP 适配器（claude-code-acp / codex-acp） | 自己装好 claude / codex CLI 与 Node.js（要 `npx`）——锦上添花，不装不影响对话 | 「找不到 npx」 |
| 浏览器插件 | Chrome | 连接失败时明说 |
| 远端会话 | 服务器上只要 sshd；本机什么都不用 | — |

第一次打开打包版时，如果这台机器上以前用 `npm run app` 跑过开发版，会**自动把旧数据目录**（`…/Electron/`）**拷一份**到新目录（`…/DAWN Science/`）：会话、provider 配置、凭证、模型目录、内核目录。只拷一次，旧目录不动。

## 签名与公证（以后有证书再做）

- macOS：删掉 `electron-builder.yml` 里 `mac.identity: null`，设 `CSC_LINK`（.p12 的路径或 base64）与 `CSC_KEY_PASSWORD`；公证再加 `afterSign` 钩子与 `APPLE_ID` / `APPLE_APP_SPECIFIC_PASSWORD` / `APPLE_TEAM_ID`。
- Windows：`WIN_CSC_LINK` / `WIN_CSC_KEY_PASSWORD`，并把 `win.signAndEditExecutable` 改回 `true`。

## 发一版（这一步以前一直没人走完，包因此从没自动上过 GitHub）

```bash
npm run release:tag -- 0.1.0    # 改 package.json 的 version、提交、打 tag v0.1.0
git push origin main
git push origin v0.1.0          # ← **只有推 tag 才会触发打包与发布**
```

然后去 Actions 看 `package` 那条；跑完在 Releases 里是一份**草稿**，看一眼再点「发布」才对外可见。

**2026-09-05 之前这条路一次都没走通**，三个原因叠在一起，缺一条都发不出来：

1. **测试卡住了发布。** 测试与打包同在一个 job，`release` 又写着 `needs: package`——Linux 那两台在测试步骤上超时（15 分钟砍掉），
   于是**已经打成功的 mac 与 Windows 产物一起作废**，只留在 artifacts 里七天后自动删除。现在测试搬去了 `ci.yml`，
   发布这条不跑测试；并且 `release` 加了 `always()`，少一个平台也照发，缺谁写在 Release 说明里。
2. **没有新 tag 就什么都不会发生。** 唯一的 `v0.0.1` 停在 2026-08-28，之后所有工作都没打过 tag，版本号也一直是 `0.0.1`。
   `npm run release:tag` 就是为了让这一步不再靠记忆。
3. **发出来的是草稿。** 这是当初有意选的（发出去之前人看一眼），但它意味着**不点那一下就没人看得见**。
   想让它推完即公开，把 `release.yml` 里 `draft: true` 改成 `false`。

## CI

- `.github/workflows/ci.yml` —— push 到 main / PR 时跑 typecheck 与 `--project node --project ui`（mac 与 Linux 两台）。
  **它红了不挡发布**，这是 2026-09-05 拆开的那一刀：验是验，发是发。
- `.github/workflows/release.yml` —— 打 `v*` tag 时四台 runner（mac / win / linux-x64 / linux-arm64）各自打包，
  汇总成一个 Release 草稿。手动触发只出 artifacts。打包前会核 **tag 与 `package.json` 的版本一致**，
  不一致当场红——否则发出去的包文件名带着旧版本号，与 Release 的标题对不上。
- **Windows 不在 `ci.yml` 的矩阵里**：这份代码还没在 Windows 上跑过（2026-08-28 首轮 25 个文件红）。
  它只在 `release.yml` 里构建打包，产物标「未经验证」。
- **已知没修的**：`--project node` 那一步在 Linux runner 上会挂死（测试跑完不退出，或某个文件卡住），
  2026-08-28 起就是这样，根因未定。现在它红在 `ci.yml` 里，不再连累发布。

## 版本号

`package.json` 的 `version` 就是安装包文件名与「关于」里的版本。用 `npm run release:tag -- <版本>` 改它并打 tag，
别手改——CI 里有一道判据核 tag 与它是否一致。
